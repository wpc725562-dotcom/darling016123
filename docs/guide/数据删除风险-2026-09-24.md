# 数据删除风险：五个维度与高危场景

> 这份文档回答一个问题：**在这台机器上删东西，最坏会坏成什么样。**
> 所有结论都来自本机实测，不是通用理论。每条都标了判例位置，可以自己去核。
>
> 写于 2026-09-24。触发原因是盘点学习资料分布时，发现三处"看起来该删、其实删了就回不来"的位置。

## 〇、结论先行

1. **「重复」这个词在本机资料盘上基本不成立。** 桌面资源包与 `D:\专升本` 曾被判为「25 个同名文件」，按相对路径复算结果是 **0 个重合**。按文件名去重，会删掉唯一副本。
2. **删除的破坏力主要沿「隐式引用」传播，而隐式引用不报错。** 本机有四种：脚本硬编码路径、生成器扫描目录、`server.js` 挂载表、以及**文档里的提及**。
3. **最危险的一类不是删错文件，是删掉「看起来是副本的同一份」。** `data/preview-root/darling016123` 是符号链接，指向笔记站的构建产物本体。
4. **「删得多」不等于「省得多」。** 本机真正值得删的重复只有 1 处、约 1.1 GB；零散小文件删掉 1000 个也省不出 100 MB。
5. **可恢复性只由两件事决定：删除方式（是否进回收站）＋ 内容是否曾进过版本控制。** 本机历史上「168 个被正文引用的文件从未 `git add`」，所以当时「git 能救」这个假设是假的。
6. **studio 是 `127.0.0.1` 的本地服务，GitHub Pages 是公网。** 这两件事的对外含义完全不同 —— 详见第六节。

## 一、为什么写这份

盘点学习资料时同时出现三个信号，指向同一类风险：

| 信号 | 实测结果 |
| :-- | :-- |
| 「桌面和 D 盘有两份资料，重复的删一份」 | 按相对路径比对：**0 个重合**。同名是巧合，来源不同（一份 paitny、一份 forestdeer），目录树完全不同 |
| 「`_pdf_cache` 是缓存，删了能重下」 | 来源是外部公众号/机构下载件，**无法保证再获取**；且被 4 个脚本硬编码引用 |
| 「`preview-root` 里的东西和 dist 重复」 | 那是**符号链接**，不是副本。删它是删本体 |

三个信号都是同一个形状：**把「看起来一样」当成「真的有一份多余」。**

## 二、五个维度

### 维度 1：数据完整性 —— 删掉之后，能不能逐字节拿回来

这是唯一不可协商的维度。其余四个维度都还有回旋余地，这一个没有：数据没了就是没了。

**三种"看着像副本、其实不是"的形态：**

**① 同名不同物。** 本机实测：

```
桌面\广东专升本资料  ∩  D:\专升本
  按「裸文件名」比对：25 个同名        ← 错的口径
  按「相对路径」比对：0 个重合          ← 对的口径
```

原因：两份资料的**来源不同**。桌面那份来自 `paitny` 系，`D:\专升本` 只有 `_pdf_cache/` 一个目录（33 个文件），来自 `forestdeer` 系。同一份卷子两个机构各自命名、各自分目录，文件名撞上很正常，路径撞上才是真重复。

对照样本：桌面资源包 vs `D:\deeepseek\zzb-真题库-source` —— **95 个文件里 94 个相对路径完全相同**。这才是真重复。

> **判据：比路径，不比文件名。** 裸文件名相同只说明"可能有关系"，说明不了"是同一份"。

**② 符号链接不是副本。** 本机实测：

```
D:/studio/data/preview-root/darling016123  →  符号链接  →  docs/.vitepress/dist
```

它看起来是个 459 MB 的目录，和 `dist` "重复"。删掉它，删的是**笔记站本体** —— studio 首页、所有 `/darling016123/` 页面立刻全 404。

两个测量工具对它的结果还不一样，这点很坑：

| 工具 | 结果 | 原因 |
| :-- | :-- | :-- |
| Python `os.walk` | 跟进链接，**重复计 459 MB** | 默认 `followlinks=True` |
| PowerShell `Get-ChildItem -Recurse` | **报 0** | 默认不跟链接 |

> **判据：算磁盘体积前先查子项是不是重解析点。**
> 注意：查**父目录** `data/preview-root` 会得到「不是重解析点」的错误答案 —— 重解析点在**子项** `preview-root/darling016123` 上。要查子项。

**③ 唯一副本可能长得像"随手下载的垃圾"。** 见维度 3 的 `_pdf_cache` 判例。

### 维度 2：一致性 —— 删除会让「同一事实的多处表述」静默矛盾

这一维度的可怕之处是**不报错**。删完之后每一处都自洽，只有把它们放在一起看才发现对不上。

**判例 A：自动算出来的数字会跟着变小，但没人记得为什么。**

`D:/studio/refs/index.html` 的头部写「共 N 份外部 PDF 原件 · X MB」。这个 N **不是手写的** —— `scripts/gen-refs-library.mjs` 的 `readPdfStats()` 会数页面里 `<tr data-k=` 的行数算出来。

于是：删掉一行手写的 PDF 行 → 头部数字静默变小。页面自洽、检查通过、没人知道少了一份什么。

**判例 B：生成区块与手写区块混在同一个文件里。**

`refs/index.html` 的结构是：

```
第 78 行   <!-- LIB:START -->     ← 生成器写入区（自产文字库，约 246 行）
第 324 行  <!-- LIB:END -->
第 326 行  起                     ← 手写区（外部 PDF 原件目录，约 400 行）
```

- 手改 `LIB:START/END` 之间的内容 → 下次跑生成器**静默回滚**。
- 删掉 `LIB:END` 以下的手写行 → 生成器**不会恢复**（它只管上面那块）。

> 判例说明：**同一个文件里可以同时存在"可再生成"和"不可再生成"的内容。** 删之前必须知道自己在哪一块里。

**判例 C：单一事实源被复制成多份。**

本机约定「学习进度唯一事实源 = `备考计划/学习进度看板.md`」。如果哪天有人把进度数抄进第二个文件，删掉其中一个不会报错，只会让两处读数不一致 —— 而且两边都"看起来是对的"。

### 维度 3：关联依赖关系 —— 破坏力沿引用链传播，而引用常常是隐式的

**本机实测：`D:\专升本\_pdf_cache` 有 4 个活消费者。**

```
笔记库/scripts/extract_paitny.py:21          SRC = ... or r"D:\专升本\_pdf_cache\paitny"
笔记库/scripts/fetch_forestdeer_pdfs.py:19   CACHE = r"D:\专升本\_pdf_cache\forestdeer"
笔记库/scripts/ocr_forestdeer_batch.py:36    CACHE = ... or r"D:\专升本\_pdf_cache\forestdeer"
笔记库/scripts/pdf_pipeline.py:11            "D:/专升本/_pdf_cache/forestdeer/英语/xxx.pdf"
```

全部是**硬编码绝对路径**，而且 `extract_paitny.py` / `ocr_forestdeer_batch.py` 还支持环境变量覆盖 —— 意味着删掉目录后，脚本可能**不会报「找不到文件」**，而是走了另一条分支，产出空结果或半截结果。

**本机四种隐式引用的形态：**

| 形态 | 位置 | 删掉源目录的后果 |
| :-- | :-- | :-- |
| 脚本硬编码路径 | 笔记库 `scripts/*.py`（4 处指向 `_pdf_cache`） | 脚本失败方式不确定，可能静默产出空结果 |
| 生成器扫描目录 | `studio/scripts/gen-refs-library.mjs` 的 `SOURCES`（3 条） | 资料库页对应区块**整块消失**，无报错 |
| 挂载表指向目录 | `studio/server.js` 的 `MOUNTS`（10 条前缀） | 该前缀在 studio 里 404，**但门户卡片还在**，点进去是坏页面 |
| **文档里的提及** | `studio/AGENTS.md` 等 | 下一个人会以为文件还在 —— 见下面的判例 |

**判例 D：文档依赖悬空（实测）。**

`studio/AGENTS.md:174` 写着：

> ⚠️ 改完 `server.js` **必须重启 43210 进程**，否则跑的还是旧代码。重启用 `restart-studio.mjs`

而 `restart-studio.mjs` **在整台机器上不存在**（在 `D:\studio`、笔记库、用户目录递归找过，只找到一个 `logs/portal-restart.out` 日志）。

> 这不是"少了个脚本"这么简单。它说明**文档本身也是引用**：文档说某文件存在，读者就会按它操作，然后在一个不存在的东西上卡住。
> **判据：把文档里的文件路径当引用去校验。** 悬空的引用比断链更隐蔽，因为没有工具会检查它。

**判据：活消费者 = 真实引用。注释、文档里的提及不算"活消费者"，但它算另一种依赖。**

### 维度 4：系统性能 —— 删除常被当作"减负"，但可能反向恶化

**判例 E：删掉"可再生成的缓存"，反而触发全量重算。**

studio 给 `/api/mistakes` 加过**文件指纹缓存 + 启动预热**（提交 `862ff0a`，首屏最慢面板 380ms → 242ms）。这个加速依赖被缓存的那个 JSON 文件存在：

- 文件在 → 指纹命中 → 直接返回缓存。
- 文件被删 → 每次请求都走"文件不存在"分支 → **要么报错、要么静默返回空**，首屏不会变快，会变空或变慢。

**判例 F：「删得多」≠「省得多」。**

盘点结果是：真正值得处理的重复只有 **1 处、约 1.1 GB**（桌面资源包 vs `zzb-真题库-source`，94/95 路径相同）。剩下能删的都是 `.bak-*` 快照和截图，合计约 2.83 MB。

> 结论：**先按体积排序，再决定删什么。** 删 1000 个几 KB 的小文件，不如处理对 1 个大目录。

**判例 G：删掉构建产物会让站点瞬间不可用。**

笔记站构建耗时 **305 秒**（`node scripts/build-docs.mjs --no-trash`）。`dist` 确实是"可再生成"的，但：

- studio 正挂着 `dist`（`MOUNTS` 里 `/darling016123`）。删掉的**那一瞬间**，studio 里所有笔记页全 404。
- 重建要等 5 分钟，而且**裸 `npm run docs:build` 会 OOM 失败**（exit 134），必须走 `build-docs.mjs`。

> **判据：「可再生成」只说明"理论上能恢复"，不说明"恢复成本可接受"。** 恢复成本要连时间、工具链、有没有人记得正确命令一起算。

### 维度 5：后续数据恢复 —— 唯一决定"删错了还能不能救"的维度

前四个维度决定"会不会坏"，这一个决定"坏了之后还能不能回头"。

**① 删除方式直接决定可恢复性。**

| 方式 | 可恢复 | 说明 |
| :-- | :-- | :-- |
| `rm` / `del /F` / `shutil.rmtree` | ✗ | 不进回收站，直接不可逆 |
| `SHFileOperationW` + `FOF_ALLOWUNDO` | ✓ | 进回收站，可还原 |
| `gio trash` / `trash-put` | ✓ | Linux 的等价做法 |

studio 自己用的就是回收站方案（见 `studio/docs/精简方案-2026-09-23.md` 的判据 E）。**这是本机唯一有先例验证过的安全删除方式。**

**② 回收站不是万无一失。**

- 回收站有**容量上限**（Windows 按盘符分配，默认约盘容量的 5%）。超出后会**静默清理最旧的项** —— 你以为还在，其实已经被系统删了。
- **清空回收站 = 二次删除**，一次点击抹掉所有"兜底"。
- 大文件（比如 1.1 GB 的目录）进回收站前要确认**目标盘剩余空间够**，否则可能直接失败或落到别的盘。

**③ Git 是另一条腿，但有前提：只有 `git add` 过的内容才能恢复。**

本机真实教训（`guide/仓库完整性审计-2026-09-21.md`）：

> **168 个被正文引用的文件从未 `git add`**，其中 **35 个已经在线渲染**。

也就是说，当时"反正 Git 里有"这个假设是**假的** —— 那些文件在版本控制里根本不存在。如果那时删了，Git 救不了。

**④ `.bak` 不是回归基线。**

studio 判据 E 明确写了这一点。`xx.css.bak-20260920` 这样的文件：

- 不知道自己是哪一版（没有版本号、没有日期语义）；
- 不会被任何检查覆盖（检查只跑当前文件）；
- 会随时间推移变成"不知道能不能删"的负担 —— 本机现有 8 个这样的文件。

> **判据：快照 ≠ 备份。** 备份要能回答"这是什么时候、相对什么版本的备份"。

**⑤ 恢复的信息成本可能高于重做成本。**

`_pdf_cache` 那 162 MB 如果删了，恢复路径不是技术问题，是**信息是否还存在**的问题：来源是外部公众号/机构下载件，能不能再找到、要不要重新付费、原帖有没有下架 —— 全都不确定。

> **判据：恢复成本要按「信息可再获取性」估，不是按「下载时间」估。**

## 三、风险最高的典型场景与前置条件

### 前置条件（叠加越多，风险越高）

| 编号 | 前置条件 | 本机对应 |
| :-- | :-- | :-- |
| **P1** | **来源不可再获取**（外部下载、别人发的、原帖已下架） | `_pdf_cache`（公众号/机构件）、桌面资源包 |
| **P2** | **无版本控制**（未 `git add`，或目录被 gitignore） | `_pdf_cache`、`data/`、桌面资料 |
| **P3** | **存在隐式消费者**（脚本硬编码、生成器扫描、挂载表、文档提及） | 4 个脚本 + `SOURCES` 3 条 + `MOUNTS` 10 条 |
| **P4** | **同一文件内混杂生成物与手写内容** | `refs/index.html`（`LIB:START/END` 上下两块） |
| **P5** | **无校验步骤**（没有删除前基线、没有删除后对比） | 没有基线记录习惯 |
| **P6** | **删除者不在上下文里**（换人 / 换会话 / 隔了很久） | 跨会话最典型 |

### 场景（按风险从高到低）

**场景 1 —— 按文件名去重清理资料盘。命中 P1 + P2 + P3。**
最危险的一个。本机旗舰判例：桌面 vs `D:\专升本` 同名 25 个、路径重合 0 个。删了就是删唯一副本，而且删完目录结构看起来依然"正常"。

**场景 2 —— 删掉"可再生成的缓存"。命中 P1 + P3。**
`_pdf_cache` 被 4 个脚本硬编码消费，同时**不可再获取**。"缓存"这个词在这里是误导 —— 它其实是**原件仓库**。

**场景 3 —— 清理"重复目录"。命中 P2 + P3 + 符号链接。**
`data/preview-root/darling016123` 是符号链接。看着重复，删了是删本体。

**场景 4 —— 重构文档 / 删旧页。命中 P3 + P4。**
生成物与手写内容混排的文件（`refs/index.html`）里，删错区块不会有任何提示。另外还要注意：仓库的 `srcExclude` 里有 9 条模式，被排除的文件**不进构建** —— 删掉它在页面上"没有变化"，但文件本身可能是某份资料的唯一副本。

**场景 5 —— 迁移目录 / 改盘符。命中 P3 + P5。**
`MOUNTS` 10 条前缀 + 4 个脚本的硬编码绝对路径 + 文档里散落的路径，全部要同步改。少改一处 = 一个静默失效的功能。

**场景 6 —— 清理构建产物。命中 P5 + P6。**
`dist` 可重建（305 秒），但 studio 正挂着它。删除瞬间站点全 404；而且重建必须用 `node scripts/build-docs.mjs --no-trash`，裸命令会 OOM。

**场景 7 —— 删掉"没用到的资源"。命中 P6。**
`D:\Study\study-tools\`（hello-algo 871 篇 + yaklang 541 篇 + DeepTutor 141 篇 + OSSU 22 篇，合计 1400+ 篇 md）**不在任何挂载表和仓库里**，所以"看起来没人用"。但它是一批开源项目的本地副本，删了要重下，而且 `study-tools` 这个名字本身就说明它当初是有意收集的。

### 本机三处删除高危点（实测清单）

| 位置 | 体积 | 为什么高危 | 建议 |
| :-- | --: | :-- | :-- |
| `D:\专升本\_pdf_cache` | 162 MB | P1+P2+P3 全中：不可再获取 + 4 脚本硬编码 + 只被生成物的手写下半部分引用 | **禁止删** |
| `data/preview-root/darling016123` | 符号链接→`dist` | 看着是副本，删掉是删笔记站本体 | **禁止删** |
| 桌面`广东专升本资料` ∩ `zzb-真题库-source` | ~1.1 GB | 94/95 路径真重复 —— **这是本机唯一可安全删一份的重复** | 保留桌面那份（`/refs/desktop` 指向它），删仓库那份 |

## 四、安全删除 SOP

复用一个已经在 studio 项目里验证过的 5 判据（出处：`studio/docs/精简方案-2026-09-23.md`）。

| 判据 | 问题 | 不通过就停 |
| :-- | :-- | :-- |
| **A 可恢复性**（首要） | 删掉之后能不能从别处**逐字节**拿回来？ | 不能 → 不删，或先备份 |
| **B 活消费者** | `grep` 全仓，有没有**真实引用**？（注释不算，文档提及算"另一种依赖"） | 有 → 先改引用再删 |
| **C 保护名单** | 是否在 `AGENTS.md` 等明文保护名单里？（优先级高于 B） | 在 → 不删 |
| **D 单一事实源** | 是不是某份事实的唯一来源？（如 `EXAM_DATE`、学习进度看板） | 是 → 不删 |
| **E 动作风险控制** | 删前建基线 → 走回收站不用 `rm` → 分批 ≤10 → 删后对比 → 确认 `.bak` 不算回归基线 | 任一步没做 → 不删 |

**执行顺序（不许跳步）：**

1. **先只读扫描，出一份报告**（路径 / 体积 / 日期）。这一步不移动、不改名、不删除。
2. 报告给使用者确认，**明确点名要删哪几个**。
3. 对确认项做**备份**（`cp -r` / `robocopy /E /COPYALL`），确认成功并告知备份位置。
4. 走**回收站**删除（不用 `rm`），**每批 ≤10 个**，每批后核对。
5. 删除后对比：体积变化、引用是否仍解析、生成器 `--check` 是否通过。

## 五、可打印自查清单

删任何东西之前，逐条打勾：

- [ ] 我确认过「这是真重复」——**按相对路径比过**，不是按文件名
- [ ] 我查过它**不是符号链接**（查的是子项，不是父目录）
- [ ] 我 `grep` 过全仓的**真实引用**（脚本 / 生成器 `SOURCES` / `MOUNTS` / 文档）
- [ ] 我确认它**不在明文保护名单**里
- [ ] 我确认它**不是某份事实的唯一来源**
- [ ] 我确认它的来源**可以再获取**（或者已经备份）
- [ ] 我建了删除前**基线**（文件清单 + 体积）
- [ ] 我走的是**回收站**，不是 `rm`
- [ ] 这一批**不超过 10 个**

## 六、边界：「上 studio」与「上公网」是两件事

这一点必须说清楚，因为它决定了"本地资料能不能放上去"。

| 通道 | 谁能访问 | 地址 |
| :-- | :-- | :-- |
| **studio** | **只有本机** | `http://127.0.0.1:43210/` |
| **GitHub Pages** | **公网所有人** | `https://wpc725562-dotcom.github.io/darling016123/` |

studio 是一个跑在本机 `127.0.0.1` 上的 Node 服务。它做的只是**把本机磁盘上的目录挂成 HTTP 前缀**，文件不复制、不上传：

```
/refs/desktop/  →  桌面\广东专升本资料          （外部 PDF 原件）
/refs/zsb/      →  D:\专升本\_pdf_cache          （外部 PDF 原件）
/refs/lib/      →  笔记库\资料                   （自产文字）
```

**结论：**

- 这些外部资料**放进 studio 是纯本机行为**，不产生任何对外发布。本机自用的学习目的下，这是可以放心做的。
- 但 `dist` 是**同一个目录既给 studio 又给 GitHub Pages**（`docs/.vitepress/dist`）。所以**一旦执行 `git push` 并触发 Pages 部署，进入 `dist` 的内容就变成公网内容**。这时外部资料的边界约束会重新生效。
- 本仓库已有对应的机制：外部大件资料通过 `srcExclude` 排除、通过 `/refs/` 挂载本机直读，**不进仓库**。这个设计正好把"本机看得到"和"公网看得到"分开了。

> 一句话：**放 studio 随便放，push 之前先想一遍。** 这两步之间没有任何自动拦截 —— 拦截只存在于"你记不记得"。
