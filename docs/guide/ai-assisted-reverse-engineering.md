# AI 辅助爬虫逆向 · 标准化方法论

> **一句话结论**：这套方法能覆盖 90% 以上的普通混淆、签名加密与动态参数场景，**原因不是 AI 变聪明了，而是流程把「破解一个网站」拆成了六步、每步都有客观判据** —— AI 只在它擅长的「读代码」环节介入，从不负责「找代码」和「保证正确」。

---

## 〇、先立规矩：适用范围与红线

这份文档是**技术方法论**，不是「破解教程」。它的合法使用边界：

| 可以做 | 不可以做 |
|:---|:---|
| 逆向**你自己的账号**能访问的内容 | 绕过**付费墙**、会员墙 |
| 提取**公开内容**做个人学习/研究 | 批量扒全站、做成公开镜像站 |
| 为**自己写**的接口做联调 | 绕过**他人系统的访问控制** |
| 抓取**你已获授权**的目标（渗透测试须有书面授权） | 破验证码做批量注册、撞库 |
| 遵守站点 ToS 与 robots、限速请求 | 高频请求打垮对方服务 |

> ⚠️ **三个「停下来」的信号**：① 目标是付费/会员内容；② 需要伪造身份或绕过实名；③ 需要攻击对方基础设施。出现任一条，**停手**。

**另有一条现实提醒**：绝大多数「要逆向」的目标，**其实不需要逆向**。第 1 步的判据会先把这类目标筛掉 —— 这既是省时间，也是守边界。

## 一、三类核心工具：各自干什么、怎么配合

先把三者的**职责边界**划清楚。搞混职责是新手最大的时间黑洞 —— 最常见的错误是「用 AI 找加密位置」，那等于让一个看不见流量的人告诉你请求发到哪了。

### 1.1 DeepSeek（或任何 LLM）：读代码的语义层

| 维度 | 内容 |
|:---|:---|
| **本质作用** | 把「机器可读的代码」翻译成「人能读的算法描述」 |
| **它拿到什么** | **只有你喂给它的文本** —— 它看不到你的网络流量、看不到浏览器状态 |
| **擅长的三件事** | ① 混淆代码的**局部**语义还原<br>② 调用栈/报错的**归因**<br>③ 已知算法的**参数提取**（key/iv/mode/padding） |
| **明确不做的三件事** | ❌ **找到**加密位置（那是抓包 + 断点的活）<br>❌ **保证**还原正确（必须本地实测等价）<br>❌ **替代**真实执行（模型说的算法必须跑一遍才算数） |
| **典型使用场景** | 给它一个 300 行的混淆函数 + 一组真实输入输出 → 要一份「这函数做了什么」的说明 |
| **已知边界** | 上下文窗口有限（别丢 10 万行进去）；会幻觉（会把相似算法说成另一种）；**对新出的风控方案知识滞后** |

> **关键认知**：LLM 的价值在于**它是唯一能「读懂」而非「解析」代码的工具**。AST 工具能把 `_0x1a2b` 改名成 `var1`，但只有 LLM 能告诉你「这段在拼一个带时间戳的签名」。这是它不可替代的地方，也是它**唯一**不可替代的地方。

### 1.2 浏览器抓包：确定「要复现哪一条请求」

| 维度 | 内容 |
|:---|:---|
| **本质作用** | 把「页面上的一个动作」映射到「一条具体的 HTTP 请求」 |
| **三个层次** | ① **DevTools Network 面板** —— 人肉看，最直观<br>② **CDP 的 `Network.*` 域** —— 程序化，可自动化<br>③ **MITM 代理**（mitmproxy/Charles）—— 抓非浏览器流量（手机 App、桌面客户端） |
| **必须拿到的产物** | URL · method · **必要 headers（UA / Referer / Cookie / 自定义签名头）** · request body · response 结构 |
| **核心技巧** | **反向筛选法**：在 Filter 框里输入「响应里必然出现的字符串」，让浏览器帮你从几百条请求里挑出那一条 |
| **判据产出** | 把请求复制成 `curl`，**逐层删头再试** —— 这决定了后面走哪条路（见 §2 Step 1） |

**为什么抓包必须排在第一位**：因为「哪些字段是算出来的」这个问题，**只有对比真实流量才能回答**。凭代码猜字段名，十个里错九个。

### 1.3 开发者工具：在运行时抓住「参数怎么算出来的」

抓包告诉你**请求长什么样**，DevTools 告诉你**这个字段是谁写的**。两者是「静态」与「动态」的分工。

| 手段 | 用途 | 什么时候用 |
|:---|:---|:---|
| **XHR/Fetch 断点** | 在请求发出**前**暂停，直接看调用栈 | 首选。能一步定位到「谁发的这条请求」 |
| **事件监听断点** | 在点击/键盘/定时器触发时暂停 | 参数由用户交互或定时器生成时 |
| **`debugger` 语句注入** | 手动在可疑行插桩 | 断点被反调试检测时 |
| **Call Stack（调用栈）** | 从「发请求」往上翻到「算参数」 | **核心操作**：找到第一个非库函数，那就是加密栈的栈底 |
| **Scope（作用域）** | 看每一帧的局部变量真值 | 确认「这个字段此刻等于什么」 |
| **Local Overrides** | 本地替换线上 JS，改一行验证假设 | 想确认「改了这行签名会不会变」 |
| **Snippets / Console** | 直接调用原函数拿真值 | Step 5 验收关口必用 |

### 1.4 三者怎么配合：一条单向流水线

```
抓包定位「请求」  →  DevTools 定位「代码位置」  →  LLM 解释「这段代码干嘛」  →  本地执行验证  →  回填到脚本
   （静态）              （动态）                    （语义）                  （验收）        （工程化）
```

**配合的三条铁律**：

1. **顺序不能倒**。先有真实流量，才有对比基准；先有代码位置，才有可读的对象。
2. **AI 只吃「已缩小」的输入**。把 10 万行丢给 LLM 是浪费；先把范围缩到一个函数（Step 2 的产物）再喂。
3. **每一步的产物必须是「下一步的输入」**。如果某步产出的是「我大概明白了」，那这步没做完。

## 二、六步标准化工作流

每一步给三样东西：**目标 · 操作要点 · 与前后步骤的衔接**。

---

### Step 1 · 抓包溯源

> **目标**：把「页面上的一个动作」映射到「一条具体的 HTTP 请求」，并**判断这条路要不要走**。

**操作要点**

1. 打开 Network，勾上 **Preserve log**（保留跨页请求）和 **Disable cache**。
2. 清空面板 → 在页面上做那个动作 → 看新出现的请求。
3. 用**反向筛选法**：在 Filter 里输入「响应里必然出现的字符串」（比如你要的那个标题），让浏览器帮你挑。
4. 优先看 **XHR/Fetch** 类型。**如果数据直接出现在 HTML 里**（右键查看源代码能看到），说明这是服务端渲染 —— **根本不需要逆向**。
5. 记录五件套：URL、method、必要 headers、request body、response 结构。

**★ 判据（这一步最重要的产出）—— 逐层删头再试**

把请求复制成 `curl`，然后**从「什么都不带」开始，一层层加回来**，看究竟卡在哪一道：

| 尝试 | 结果的含义 |
|:---|:---|
| ① 裸请求（无任何头）就通 | **完全不需要逆向**，直接写脚本 |
| ② 加一个 `User-Agent` 就通 | **不需要逆向** —— 只是反「非浏览器」，加头即可 |
| ③ 加 `Referer` 才通 | **不需要逆向** —— 热链保护 |
| ④ 加 `Cookie`/`token` 才通 | 关卡是**登录态**，不是签名 → 走扫码登录，不逆向 |
| ⑤ 全都带上还是被拒 | **真的需要逆向**，进 Step 2 |

> **实测样例（本项目 2026-09-18，B站）**：
>
> | 请求头组合 | `x/web-interface/wbi/view` |
> |:---|:---|
> | 无任何头 | **HTTP 412 被拒** |
> | 只加 `User-Agent` | **HTTP 200, code=0 ✅** |
> | UA + Referer | HTTP 200, code=0 |
> | UA + Referer + SESSDATA | HTTP 200, code=0 |
>
> 注意这个端点的路径里带 **`wbi`** —— 也就是 B站那套著名的签名体系。但**不带任何签名参数（`w_rid` / `wts`）也能通过**。
> **结论**：这个端点的关卡是「你是不是浏览器」，不是「你有没有签名」。一个 `User-Agent` 就解决了。

**衔接**：产出「目标请求清单 + 关卡类型判定」。
- 若判定为 ①②③④ → **直接跳到 Step 6**（写采集器），Step 2–5 全部跳过。
- 若判定为 ⑤ → 进 Step 2。

---

### Step 2 · 定位加密栈

> **目标**：找出「**哪个字段**是算出来的」以及「**在哪一行**算的」。

**操作要点**

1. **字段差分**（先做这个，比搜代码快得多）：
   - 同一个动作发两次，对比两次的请求 body / query。
   - **变化的字段** = 候选动态参数（`timestamp`、`nonce`、`sign`、`token`、`_t`）。
   - **不变的字段** = 静态参数，不用管。
2. 对变化的字段**下 XHR 断点**：Sources → XHR/fetch Breakpoints → 添加 URL 片段 → 重新触发动作。
3. 命中后看 **Call Stack**，**从下往上翻**，找到**第一个不是第三方库**的帧 —— 那就是加密栈的栈底。
4. 搜代码的**三把钥匙**（断点不方便时用）：
   - 字段名本身（`sign`、`_signature`）
   - 算法关键词（`md5`、`sha`、`aes`、`encrypt`、`CryptoJS`）
   - **请求 URL 的路径片段**（这个最有效 —— 加密函数常和接口路径写在一起）
5. **★ 分清两件事**：
   - **参数在哪「拼」** —— 通常在**调用点**（`data = {a:1, b:2, sign: calc(...)}`）
   - **参数在哪「算」** —— 在**被调函数内部**
   新手常把「拼接点」当成「加密点」，结果抄了一堆没用的代码。

**衔接**：产出「**加密函数源码 + 一组真实输入输出**」。
- 这一步的产物就是 Step 3 的输入。
- ⚠️ **如果加密函数在 WASM 里 / 在原生代码里**（Call Stack 出现 `wasm-function[...]` 或找不到 JS 帧）→ **超出本方法论范围**，见 §3.4。

---

### Step 3 · 剥离混淆 JS

> **目标**：把「不可读的一段」变成「能读懂的一段」。

**操作要点**

1. **先分类，再选工具**。混淆不是一个东西，四类的处理方式完全不同：

| 混淆类型 | 特征 | 处理方式 |
|:---|:---|:---|
| **压缩/美化** | 单行超长、变量名短但可读 | DevTools 的 **Pretty print**（`{}` 按钮）就够了 |
| **字符串数组 + 解码器** | 开头一个大数组，通篇 `_0x1a2b(0x3f)` | **AST 工具**（webcrack / js-deobfuscator） |
| **控制流平坦化** | 一个 `while(true) + switch` 包住所有逻辑 | **AST 工具**（同上），需多次迭代 |
| **反调试/自保护** | 一开 DevTools 就死循环、`debugger` 刷屏 | **先摘掉保护**，再处理上面三类 |

2. **工具顺序（从轻到重）**：
   ```
   DevTools Pretty print  →  通用 AST 工具  →  LLM 局部解释
        （10 秒）              （1 分钟）        （只在 AST 搞不定时用）
   ```
3. **★ 不要一开始就把整份文件丢给 LLM**。正确做法：先用 AST 工具还原结构，再把**一个函数**（Step 2 的产物）交给 LLM 解释。
4. **只读、不改语义**：还原后要能跑出**同样的结果**。改不出同样结果 = 还原错了。

**衔接**：产出「**可读的目标函数**」。它是 Step 4 的唯一输入。
- ⚠️ 若还原后仍然看不懂（大量自定义编码表、虚拟机式混淆）→ 回到 Step 2 换个断点位置，**找一个更「外层」的函数**（越外层越接近明文）。

---

### Step 4 · AI 辅助逻辑推演

> **目标**：把「可读的代码」变成「可复现的算法描述」。

**★ 这一步是「不依赖玄学提示词」的关键所在。** 秘诀不是措辞，而是**把输入给足**：

**三件套输入（缺一不可）**

```
① 函数源码     —— Step 3 的产物
② 一组真实输入 —— 从 Step 2 的断点里抄下来的实际参数值
③ 对应的真实输出 —— 从 Console 里调用原函数拿到的真值
```

**提问模板（不是话术，是「把上下文结构化」）**

| 目的 | 提问方式 |
|:---|:---|
| **算法归纳** | 「这是加密函数。输入是 `<真实值>`，输出是 `<真实值>`。请说明它的算法步骤，并指出所有魔数/常量分别代表什么。」 |
| **参数溯源** | 「这是调用栈。请说明参数 `A` 是从哪里来的，经过了哪些变换。」 |
| **差异定位** | 「我按上面的描述用 Python 复现，得到 `<我的值>`，但真实值是 `<真值>`。请指出哪一步可能不等价。」 |
| **标准算法识别** | 「这段代码看起来是标准算法。请指出具体是哪种，以及 key / iv / mode / padding 各是什么。」 |

**三条硬约束（贴在墙上）**

1. **输入必须真实** —— 拿假数据问，得到的答案是假的。
2. **输出必须可验证** —— 每个结论都要能在 Step 5 跑一遍。
3. **必须要求它标注不确定处** —— 加一句「不确定的地方请明确标出，不要猜」。**这一句能消掉大部分幻觉。**

**衔接**：产出「**算法说明书 + 待验证的 Python 实现**」。
- ⚠️ 注意：这一步的产出**全部是「假设」**，不是「结论」。只有 Step 5 跑通才升级为结论。

---

### Step 5 · 本地环境调试

> **目标**：**证明**你的复现和浏览器算出来的一模一样。这是整个流程的**验收关口**。

**操作要点**

1. **等价性验证（三件套闭环）**：
   ```
   同一组输入  →  浏览器 Console 调用原函数 → 真值 A
               →  你的本地实现           → 值 B
               →  断言 A == B
   ```
   在 Console 里直接调原函数是最可靠的手段 —— 不用猜，真值就在那。

2. **常见不等价原因（按实际出现概率排序）**：

| # | 原因 | 表现 | 排查 |
|:--:|:---|:---|:---|
| 1 | **编码差异** | 值差几个字符 | UTF-8 vs GBK、URL 编码、Base64 变体（`+/` vs `-_`） |
| 2 | **参数顺序 / 分隔符** | 完全不同的哈希 | 打印两边**拼接后的原始字符串**逐字符比 |
| 3 | **时间戳精度** | 偶发失败 | 秒 vs 毫秒；本机时钟偏移 |
| 4 | **随机数 / nonce 来源** | 每次都不同 | 确认随机数是否参与签名、是否服务端下发 |
| 5 | **隐式依赖** | 首次调用失败 | 是否需先调某个初始化函数（`window.__init()`） |
| 6 | **空值处理** | 边界值失败 | `null` / `undefined` / 空串分别怎么拼 |

3. **⚠️ 不要用「反正能用」放过差异**。签名只要差一位，通常**当场失败**；如果「差一位还能用」，说明它其实不校验 —— 那更该回头确认是不是漏了什么。

**衔接**：产出「**已验证的算法 + 可运行的本地脚本**」。
- 这一步通过 → 算法问题**已解决**，进 Step 6。
- 这一步不通过 → **回到 Step 2** 换断点位置（多半是断错了函数，或漏了前置调用）。

---

### Step 6 · 全站适配复用

> **目标**：从「一条请求」变成「一套能长期用的采集器」。

**操作要点**

1. **把签名器抽成独立模块**：输入参数 `dict` → 输出签名 `dict`。**不要把它和业务逻辑混在一起** —— 签名是最易变的部分，要能单独替换。
2. **会话与登录态管理**：
   - cookie/token **持久化**到本地（注意别提交进 git）。
   - 过期检测 + 自动刷新或提示重新登录。
3. **限速与退避**：
   - 固定间隔 + 抖动（不要精确等间隔，那本身是机器人特征）。
   - 对 **412 / 403 / 429** 分别处理：412 多为头校验、403 多为热链/权限、429 为限流。
4. **缓存与断点续传**：
   - 已完成的单元**落盘并跳过**。
   - **★ 写盘用「临时文件 + 改名」**，避免中断留下半截文件被误判为「已完成」。
5. **监控与告警**：签名失败率、字段缺失率。**一旦失败率上升，回到 Step 1 重新差分字段**。

**衔接**：闭环。**Step 6 → Step 1**。接口改版是常态，不是意外。

### 工作流全景

| 步 | 目标 | 核心产出 | 失败时回到 |
|:--:|:---|:---|:---|
| 1 | 抓包溯源 | 请求清单 + **关卡类型判定** | — （起点） |
| 2 | 定位加密栈 | 加密函数 + 真实输入输出 | Step 1（换请求） |
| 3 | 剥离混淆 | 可读的目标函数 | Step 2（换断点位置） |
| 4 | AI 逻辑推演 | 算法说明书（**假设**） | Step 3（还原不彻底） |
| 5 | 本地调试 | **验证通过的实现**（结论） | **Step 2**（断错函数） |
| 6 | 全站适配 | 可长期运行的采集器 | **Step 1**（接口改版） |

## 三、为什么能覆盖 90% 以上（且不依赖玄学提示词）

### 3.1 先看清三类场景的真实分布

「90%」这个数不是拍脑袋，而是因为**问题本身的分布是极度偏斜的**：

| 类别 | 说明 | 大致占比 | 需要逆向吗 |
|:---|:---|:---:|:---|
| **A 类：根本不需要逆向** | 裸请求/加 UA/加 Referer/带登录态就能通 | **最大一块** | ❌ |
| **B 类：标准算法 + 明文参数拼接** | MD5 / SHA / HMAC / AES + timestamp / nonce | **逆向的绝对主力** | ✅ 但很规则 |
| **C 类：自定义算法 / 强混淆 / 风控** | 风控 JS、WASM、设备指纹、行为检测 | 少数 | ✅ 且很难 |

**★ 关键洞察**：**A 类被 Step 1 一个判据就吃掉了**，而 C 类本来就不是「标准化流程」能覆盖的（见 §3.4）。真正需要这套方法论的是 **B 类** —— 而 B 类恰恰是**最规则、最可标准化**的一类：算法是现成的（MD5/AES 就那么几种），难的是「找到它」和「拼对参数」，这两件事都**有确定性做法**。

### 3.2 覆盖率的来源：每一步都有客观判据

「不依赖玄学」的真正含义是：**流程里没有一个环节需要「运气」或「灵感」**。

| 步 | 客观判据（不是感觉） |
|:--:|:---|
| 1 | **逐层删头**：能通 / 不能通，是二元事实 |
| 2 | **字段差分**：两次请求 diff，变的字段就是候选 —— 不需要猜 |
| 3 | **混淆四分类**：看一眼特征就知道用哪个工具，是分类问题不是创造问题 |
| 4 | **三件套输入**：输入输出都是真值，模型的活是「归纳」不是「猜」 |
| 5 | **等价断言**：`A == B` 是布尔值，没有中间地带 |
| 6 | **失败率**：数字会说话 |

**把这套流程和「玄学提示词」对比**：

| 维度 | 玄学提示词 | 本方法论 |
|:---|:---|:---|
| 输入 | 「帮我破解这个网站」 | 函数源码 + 真实输入 + 真实输出 |
| 对 AI 的期待 | 直接给答案 | 只做「读代码」这一件事 |
| 正确性判定 | 「感觉对了」 | 本地跑出等价值 |
| 失败时 | 换一句提示词再试 | **回到具体某一步**，用判据定位 |
| 可复用性 | 换个网站就失效 | 换个网站照跑 |

### 3.3 为什么「切小问题」比「提示词技巧」有效得多

LLM 的能力边界是明确的：**它擅长在给定上下文里做归纳，不擅长在没有上下文时做检索**。

- 「帮我破解这个网站」= 要求它**检索**一个它看不到的东西 → **必然幻觉**。
- 「这是加密函数，输入 X 输出 Y，说清算法」= 要求它**归纳**眼前的代码 → **高度可靠**。

**所以这套方法论的本质是：用前 3 步（全是确定性操作）把问题缩小到「一个函数 + 一组真值」，让第 4 步变成一个 LLM 一定能做好的任务。** 提示词写得好不好，在这套流程里**几乎不影响结果** —— 因为上下文已经给足了。

### 3.4 覆盖不到的那 10%（诚实的边界）

| 场景 | 为什么覆盖不了 | 出路 |
|:---|:---|:---|
| **WASM 加密** | 算法在二进制里，Call Stack 无 JS 帧 | 需要专门的 WASM 工具链（反汇编/插桩） |
| **原生代码加密（App）** | 不在浏览器里 | MITM + 证书固定绕过 + Frida |
| **设备指纹 + 行为风控** | 这不是「算参数」问题，是「像不像人」问题 | 换思路：用真实浏览器自动化，而不是复现算法 |
| **验证码 / 滑块** | 需要视觉或行为模拟 | 打码服务、或改用真实浏览器 |
| **服务端强校验** | 签名对了但服务端另有判据（IP/频次/账号画像） | 换 IP、降频、换账号策略 |
| **VM 式混淆（自定义字节码）** | AST 还原后仍是解释器循环 | 动态插桩（在解释器 dispatch 处打点） |

> **诚实提示**：这 6 类占了「难啃的 10%」，但它们**恰好也是最容易被误判为「90% 都搞不定」的那部分** —— 因为遇到它们的人会在论坛上发帖，而顺利跑完 B 类的人不发帖。**样本偏差会让人低估这套方法论的覆盖率。**

## 四、AI 辅助的切入点与适用边界（逐步骤对照）

| 步 | AI 介入程度 | ✅ 适合 AI 做 | ❌ 必须人/工具做 |
|:--:|:---|:---|:---|
| **1 抓包溯源** | ⚪ 几乎不介入 | 解释响应 JSON 的结构 | **定位请求**（必须看真实流量） |
| **2 定位加密栈** | 🔵 辅助 | 解释调用栈各帧在干什么 | **下断点、读变量**（必须运行时） |
| **3 剥离混淆** | 🟢 **主力** | 混淆分类、局部还原、解释还原结果 | **大规模 AST 变换**（用工具，比 LLM 准） |
| **4 逻辑推演** | 🟢 **主力** | 算法归纳、魔数解释、差异定位 | **保证正确性**（必须实测） |
| **5 本地调试** | 🔵 辅助 | 报错归因、不等价原因排查 | **判定是否等价**（必须跑） |
| **6 全站适配** | 🔵 辅助 | 写采集器骨架、抽签名模块、写重试 | **限速策略、风控应对**（需判断与责任） |

### 三条硬边界

1. **AI 不接触真实流量** —— 它看不到请求、看不到浏览器状态。**所有「定位类」工作都与它无关。**
2. **AI 的输出永远是「假设」** —— 只有 Step 5 跑通才升级为「结论」。**不要跳过验证。**
3. **AI 的知识有滞后** —— 新出的风控方案它不认识。此时**回到 Step 2**（看真实代码），而不是换提示词。

### 一条实用判据：什么时候不该用 AI

| 信号 | 该做什么 |
|:---|:---|
| 代码超过 500 行 | 先用 AST 工具缩小范围 |
| 需要「找」而不是「解释」 | 用 DevTools，别问 AI |
| AI 给了三种不同答案 | 它没把握 → 补足「三件套输入」重问 |
| 想让它「猜」算法参数 | **去 Console 调原函数拿真值** |
| 已经问了三轮还没进展 | **回到 Step 2 换个断点位置** |

## 六、评估：这些项目能更好地用于「B站学习资料提取」吗？

### 6.1 先给结论

> **不能。而且不是「差一点」，是「用不上」。**
> B站 学习资料提取的瓶颈**不在 JS 逆向**，装 JS 逆向工具链**收益接近于零**。

### 6.2 证据：B站 的两道关卡都不是签名

本项目 2026-09-18 实测（同一台机器、同一账号）：

| 接口 | 关卡 | 实测 |
|:---|:---|:---|
| `x/web-interface/wbi/view`（元数据） | **User-Agent** | 裸请求 412 → **只加 UA 就 200** |
| `x/player/v2`（字幕轨） | **登录态** | 未登录 0 轨 → **带 SESSDATA 就 1 轨** |

**两个都是「头/身份」问题，不是「算参数」问题。**

- 路径里明明写着 **`wbi`**（B站著名的签名体系），但**不算 `w_rid` / `wts` 也能通过**。
- 字幕轨的 `need_login_subtitle` 是**服务端按登录态返回的** —— 登录了它直接给你现成的字幕，**根本不需要 ASR，更不需要逆向**。

> **换句话说**：B站 这个场景连 §3.1 的 **B 类**（标准算法 + 签名）都不是，它属于 **A 类（根本不需要逆向）**。

### 6.3 真正的瓶颈在哪（都不是逆向问题）

| 真实瓶颈 | 表现 | 解法 |
|:---|:---|:---|
| **登录态** | 未登录拿不到字幕轨、音频 CDN 被截断（实测只下到 0.19 MB，正常 14 MB） | 扫码登录拿 SESSDATA |
| **Referer / UA** | 无 Referer 时 CDN 403 | 固定请求头 |
| **限速** | 高频请求被拒 | 并发 + 抖动；本项目实测 6 线程 110 个/分 稳定 |
| **体量** | 1526 个分P / 470 小时 | **并行下载 + 断点续传**（串行 11 个/分 → 并行 110 个/分） |
| **内容理解** | 470 小时视频没法看 | 字幕 → Q&A 提炼（这是 LLM 真正的用武之地） |

> **注意最后一行**：在这个场景里，**LLM 最大的价值不是「逆向」，而是「把 470 小时视频变成可复习的结构化笔记」** —— 那是 §1.1 说的「读代码的语义层」在**读讲解**上的同类应用。方向对了，价值大得多。

### 6.4 什么情况下才需要给 B站 上逆向工具链

**触发条件（满足任一条）**：

1. `playurl` 开始**强制校验 `w_rid` 签名**（届时需要逆向 wbi 算法：`img_key`/`sub_key` 混合 → 重排 → 加 `wts` → MD5）。**到那时 §2 的六步流程正好适用**：抓包差分（`wts`/`w_rid` 会变）→ XHR 断点 → 找 `wbi` 函数 → LLM 解释重排表 → 本地验证。
2. 出现**设备指纹/风控挑战**（如返回 `-352` 风控码）。
3. 需要抓 **App 端独有**的内容（需 MITM + 证书固定绕过）。

**当前这三条都不成立。**

### 6.5 可落地建议（按投入产出排序）

| 优先级 | 建议 | 理由 | 成本 |
|:--:|:---|:---|:---|
| **P0** | **继续用现有自研脚本**（零依赖） | 已实测跑通；无第三方依赖、无许可风险、无供应链风险 | 0 |
| **P0** | **把并行 + 断点续传 + `.part` 改名**固化进脚本 | 这是唯一实测有效的加速手段（**9 倍**） | 已做 |
| **P1** | **给 LLM 的活是「字幕 → Q&A 提炼」**，不是逆向 | 这才是本场景的价值点（470 小时 → 结构化笔记） | 低 |
| **P2** | 想省事时用 **`yt-dlp`** 兜底 | 已验证；B站 extractor 内置 | 低 |
| **P3** | 只在需要时**临时**装 `js-reverse-mcp` | 若 B站 真上了强制签名，它能把 Step 2–5 自动化 | 中（Node 20+） |
| **❌** | ~~装 JSHookMCP 抓 B站~~ | 723 工具里用得上 0 个；AGPL-3.0 还有商用许可问题 | — |
| **❌** | ~~装 reverse-skill（36k 星）~~ | 面向渗透/CTF，需要授权书；**用于提取学习资料是用错工具** | — |

### 6.6 一句话总结

> **方法论是对的，但它要解决的问题在 B站 这个场景里不存在。**
> 把「逆向工具链」的投入挪到「字幕 → 结构化笔记」上，产出会高一个数量级。
> 唯一值得保留的是**这套六步流程本身** —— 它是「万一哪天关卡变了」的现成预案，成本只是记住它。
