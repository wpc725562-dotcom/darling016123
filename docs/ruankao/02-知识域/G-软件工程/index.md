## 本域考法

上午场以单选出现，题干通常是一个场景描述 + "以下说法正确的是"。
**不考背诵定义，考"给个场景判断属于哪一类"**。所以每个知识点都要记"特征词"。

典型问法：
- "某项目需求不明确，应采用哪种开发模型？"（考 G1）
- "以下哪种内聚程度最高？"（考 G3）
- "该测试方法属于黑盒还是白盒？"（考 G4）
- "关键路径是哪条？项目最短工期是多少？"（考 G7）

## G1 生命周期与开发模型 ★★★ L2

### 必须记住的五个模型

| 模型 | 特征词 | 适用场景 |
|:---|:---|:---|
| **瀑布** | 阶段严格顺序、文档驱动、不可回溯 | 需求明确且稳定 |
| **原型** | 快速构建可运行版本给用户看 | **需求不明确**，需要澄清 |
| **螺旋** | 螺旋式上升、每个循环含风险分析 | **风险大**的大型项目 |
| **增量** | 分批交付，每批可用 | 可以分块上线 |
| **敏捷** | 迭代、拥抱变化、可工作软件优于文档 | 需求变化快 |

**V 模型**：瀑布的变体，强调**测试与开发阶段一一对应**（需求↔验收测试、设计↔集成测试、编码↔单元测试）。考题常问"哪个测试对应概要设计"→ 集成测试。

### 易错点

- 螺旋模型的核心是**风险分析**，不是"反复做"。看到"风险"选螺旋。
- 原型模型分两种：**抛弃型**（只为澄清需求，最后扔掉）和**演化型**（逐步演变成产品）。题目若说"原型最终被丢弃"选抛弃型。
- 敏捷不是"没有文档"，是"可工作软件优于详尽文档"。

## G2 需求分析（DFD / 数据字典）★★★ L2

### 数据流图四元素（必背）

| 元素 | 图形 | 说明 |
|:---|:---|:---|
| **外部实体** | 矩形 | 系统之外的人/组织/系统 |
| **加工（处理）** | 圆角矩形或圆 | 对数据做变换 |
| **数据流** | 箭头 | 数据流动方向，**必须命名** |
| **数据存储** | 开口矩形或双横线 | 数据库/文件 |

**分层 DFD**：顶层图（只有一个加工，展示系统与外部实体的关系）→ 0 层图 → 1 层图……**父子图平衡**：父图中某加工的输入输出，必须与子图中对应。

### 数据字典

四类条目：**数据项、数据结构、数据流、数据存储**。加工不在数据字典里（在 DFD 里）。

### 易错点

- **数据流不能双向**。两个方向的数据必须画两条箭头。
- **父子图不平衡**是最常见的错误选项——子图多出父图没有的输入/输出。
- 外部实体之间**不能直接有数据流**，必须经过加工。

### 判定表与判定树（教材 6.1.4 补充）

> 原版本遗漏，2026-10-29 补入。DFD 表达不了"在什么条件下做什么"，这时用判定表。

#### 判定表的四部分

| 部分 | 位置 | 内容 |
|:---|:---|:---|
| **条件桩** | 左上 | 列出所有条件 |
| **条件项** | 右上 | 每个条件在各规则下的取值（Y/N） |
| **动作桩** | 左下 | 列出所有动作 |
| **动作项** | 右下 | 每个动作在各规则下是否执行（✓/空） |

**例**（两个条件）：

| | 规则1 | 规则2 | 规则3 | 规则4 |
|:---|:---:|:---:|:---:|:---:|
| 条件1 | Y | Y | N | N |
| 条件2 | Y | N | Y | N |
| 动作1 | ✓ | | ✓ | |
| 动作2 | | ✓ | | ✓ |

#### 规则数计算（偶尔考）

**规则数 = 2^条件数**

- 2 个条件 → 4 条规则
- 3 个条件 → 8 条规则
- 4 个条件 → 16 条规则

#### 判定树

把判定表画成树形，更直观。条件少时用表，条件多时用树。

**教材的说法**：判定表适合**条件组合不多**的场景，条件一多表会爆炸。

## G3 软件设计（内聚与耦合）★★★ L2

### 内聚：从低到高（越高越好）

| 等级 | 名称 | 特征 |
|:---:|:---|:---|
| 1（最低） | 偶然内聚 | 模块内各部分毫无关系 |
| 2 | 逻辑内聚 | 由参数决定执行哪个逻辑 |
| 3 | 时间内聚 | 需要在同一时间段执行 |
| 4 | 过程内聚 | 必须按特定次序执行 |
| 5 | 通信内聚 | 操作同一数据结构 |
| 6 | 顺序内聚 | 输出作为下一部分输入 |
| 7（最高） | **功能内聚** | 所有部分共同完成**一个**功能 |

**记忆口诀**：偶逻时过通顺功（偶然-逻辑-时间-过程-通信-顺序-功能）。

### 耦合：从低到高（越低越好）

| 等级 | 名称 | 特征 |
|:---:|:---|:---|
| 1（最低） | **非直接耦合** | 模块间无直接联系 |
| 2 | 数据耦合 | 只传简单数据参数 |
| 3 | 标记耦合 | 传整个数据结构 |
| 4 | 控制耦合 | 传控制信息（开关量） |
| 5 | 外部耦合 | 依赖外部环境 |
| 6 | 公共耦合 | 共享全局数据区 |
| 7（最高） | **内容耦合** | 直接访问另一模块内部 |

**目标**：**高内聚、低耦合**。

### 易错点

- 题目问"最高的内聚"→ 功能内聚；"最低的耦合"→ 非直接耦合。
- 数据耦合 vs 标记耦合：传 `int age` 是数据耦合，传整个 `Student` 对象是标记耦合。
- 控制耦合的标志是**传了 if/switch 的判断条件**。

## G4 软件测试 ★★★ L3

### 黑盒测试（不看代码，看功能）

| 方法 | 怎么用 |
|:---|:---|
| **等价类划分** | 把输入分成有效/无效等价类，每类取一个代表 |
| **边界值分析** | 取边界及其两侧，如 [1,100] 取 0,1,100,101 |
| **因果图** | 输入条件与输出结果的逻辑组合 |
| **错误推测** | 凭经验猜哪里容易错 |

### 白盒测试（看代码结构）

| 覆盖准则 | 强度 | 说明 |
|:---|:---:|:---|
| 语句覆盖 | 最弱 | 每行代码至少执行一次 |
| 判定覆盖（分支） | ↑ | 每个判断的真假都出现 |
| 条件覆盖 | ↑ | 每个条件的真假都出现 |
| 判定/条件覆盖 | ↑ | 同时满足两者 |
| 条件组合覆盖 | ↑ | 每个判断中条件的所有组合 |
| **路径覆盖** | 最强 | 所有可能路径 |

**记忆**：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径。

### 测试阶段对应关系

| 测试 | 对象 | 依据 |
|:---|:---|:---|
| 单元测试 | 模块 | 详细设计 |
| 集成测试 | 模块间接口 | 概要设计 |
| 系统测试 | 整个系统 | 需求规格 |
| 验收测试 | 用户视角 | 用户需求 |

### 易错点

- **语句覆盖不能保证判定覆盖**（可能只走了真的分支）。
- **条件覆盖不一定满足判定覆盖**，反之亦然——所以有"判定/条件覆盖"。
- 题目给一段代码问"最少几个测试用例达到判定覆盖"，要数判断分支数（通常 2 个判断 → 2 个用例）。

## G5 软件维护 ★★ L1

| 类型 | 目的 | 占比 |
|:---|:---|:---:|
| 正确性维护 | 改 bug | 约 20% |
| 适应性维护 | 适应外部环境变化（新系统、新硬件） | 约 25% |
| **完善性维护** | **增加新功能、提升性能** | **约 50%（最大）** |
| 预防性维护 | 为将来可维护性做改造 | 约 5% |

**必记**：完善性维护占比最大。这是高频考点。

## G6 软件质量与评审 ★★ L1

- **评审越早，修复成本越低**。需求评审发现的问题，修复成本是上线后发现的 1/100。
- 正式技术评审（FTR）关注：产品是否符合规格说明。
- 软件质量属性：功能性、可靠性、易用性、效率、可维护性、可移植性。

## G7 项目管理（甘特图 / PERT / 关键路径）★★★ L3

### 甘特图 vs PERT 图

| | 甘特图 | PERT 图 |
|:---|:---|:---|
| 形式 | 横道图，时间轴 | 网络图，节点+箭线 |
| 强项 | 直观展示进度 | 展示**依赖关系**、算关键路径 |
| 弱项 | 看不出依赖 | 不直观 |

### 关键路径算法（必考）

1. 画出网络图，标出每个活动的工期
2. 从起点到终点，找出**所有路径**
3. 每条路径的工期相加
4. **工期最长的路径 = 关键路径**，其长度 = 项目最短工期

**关键性质**：
- 关键路径上的活动**总时差为 0**，任何延误都会导致项目延期
- 关键路径可能不止一条
- 缩短工期必须缩短关键路径上的活动

**总时差** = 最晚开始时间 − 最早开始时间 = 最晚完成 − 最早完成

### 易错点

- 关键路径是**最长**路径，不是最短。很多人直觉选最短，错。
- 题目问"某活动延误 3 天，项目是否延期"→ 看它在不在关键路径上；在则延期，不在则看总时差够不够吸收。

## G8 风险管理 ★ L1

过程：风险识别 → 风险预测（概率+影响）→ 风险应对计划 → 风险监控

四种应对策略：
- **回避**：改变计划，绕开风险
- **转移**：买保险、外包
- **减轻**：降低概率或影响
- **接受**：认了，准备应急储备

## G10 配置管理 ★★ L1

> **教材 5.8，原版本遗漏，2026-10-29 补入**。

### 配置项

需要**版本控制**的所有产出：代码、文档、数据、工具。

### 五项活动

| 活动 | 做什么 |
|:---|:---|
| **配置标识** | 给每个配置项编号、定版本 |
| **版本控制** | 管理不同版本的并存与回溯 |
| **变更控制** | 变更申请 → 评估 → 批准 → 实施 → 验证 |
| **配置审计** | 确保实际状态与记录一致 |
| **状态报告** | 记录配置项的状态变化 |

### 基线（Baseline）

**定义**：经过评审、被正式确认的配置项集合。

**关键规则**：**基线一旦建立，修改必须走变更控制流程**。

**三种基线**：
- 功能基线（需求确定后）
- 分配基线（设计确定后）
- 产品基线（产品交付时）

### 易错点

- 配置管理管的不只是**代码**，还包括文档、数据
- **基线不是"冻结"**，是可以改的，但要走流程
- 变更控制的核心是"**评估影响**"，不是"禁止变更"

## G11 软件危机与软件工程原则 ★ L1

> **教材 5.1，原版本遗漏，2026-10-29 补入**。偶尔考概念。

### 软件危机

**表现**：开发生产率跟不上硬件发展、成本超支、进度延误、质量不可靠、难以维护。

**三个原因**：
1. 软件规模越来越大，复杂度急剧上升
2. 缺乏有效的工程化方法
3. 忽视需求分析和文档

**1968 年北约会议**首次提出"软件工程"这个名词——这是常考的"第一次"。

### 软件工程七条基本原理（Boehm）

1. 用分阶段的生命周期计划严格管理
2. 坚持进行阶段评审
3. 实行严格的产品控制（基准配置管理）
4. 采用现代程序设计技术
5. 结果应能清楚地审查
6. 开发小组的人员应少而精
7. **承认不断改进软件工程实践的必要性**

**常考问法**："以下哪条不属于软件工程基本原理"——干扰项通常是"使用最新的开发工具"这类（工具不是原理）。

### 质量管理：QA vs QC

| | QA（质量保证） | QC（质量控制） |
|:---|:---|:---|
| 导向 | **过程** | **产品** |
| 做法 | 确保过程正确（预防） | 检查产品是否合格（检测） |
| 时机 | 事前 | 事后 |

**一句话**：**QA 管过程，QC 管产品**。
