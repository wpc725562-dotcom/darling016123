## C1 三级模式与两级映像 ★★★ L1

### 三级模式

| 模式 | 别称 | 描述什么 | 数量 |
|:---|:---|:---|:---|
| **外模式** | 子模式 / 用户模式 | 用户看到的数据视图 | 多个 |
| **模式** | 逻辑模式 / 概念模式 | 全体数据的逻辑结构 | **只有一个** |
| **内模式** | 存储模式 / 物理模式 | 数据在磁盘上怎么存 | **只有一个** |

### 两级映像与独立性

| 映像 | 作用 | 保证什么 |
|:---|:---|:---|
| **外模式/模式** | 模式变了，改映像，外模式不变 | **逻辑独立性** |
| **模式/内模式** | 存储变了，改映像，模式不变 | **物理独立性** |

**必考**：外模式/模式 → 逻辑独立性；模式/内模式 → 物理独立性。这两个别搞反。

## C2 E-R 模型与转换 ★★★ L2

### 三要素

| 元素 | 图形 | 说明 |
|:---|:---|:---|
| **实体** | 矩形 | 客观存在的事物，如"学生" |
| **属性** | 椭圆 | 实体的特征，如"学号" |
| **联系** | 菱形 | 实体间的关系，如"选修" |

### 联系的类型与转换规则（下午场核心）

| 联系类型 | 转换方法 |
|:---|:---|
| **1:1** | 可以把一方的主键放到另一方作为外键，或单独建表 |
| **1:n** | **把 1 端的主键放到 n 端作为外键** |
| **m:n** | **必须单独建一张表**，主键是两个实体主键的组合 |

**例**：学生（学号）与课程（课程号）是 m:n 的"选修"关系，且选修有属性"成绩"。
→ 建表 `选修(学号, 课程号, 成绩)`，主键是 `(学号, 课程号)`。

### 易错点

- **m:n 联系不能合并到任一方**，必须单独成表。
- 1:n 联系中，外键放在**多**的那一端。比如"班级—学生"是 1:n，外键"班级号"放在学生表里。
- 联系也可以有属性（如"选修"有"成绩"），转换时要带上。

## C3 关系代数 ★★★ L2

### 五个基本运算

| 运算 | 符号 | 作用 | 类比 SQL |
|:---|:---:|:---|:---|
| **投影** | π | **选列**（垂直） | SELECT 列名 |
| **选择** | σ | **选行**（水平，按条件） | WHERE |
| **并** | ∪ | 合并两个结果集（去重） | UNION |
| **差** | − | 在 A 不在 B | EXCEPT |
| **笛卡尔积** | × | 两表所有组合 | CROSS JOIN |

### 派生运算

| 运算 | 符号 | 说明 |
|:---|:---:|:---|
| **交** | ∩ | 同时属于两者 |
| **自然连接** | ⋈ | 按同名属性等值连接，**结果去掉重复属性** |
| **除** | ÷ | 用于"对所有…"的查询 |

**记忆**：π 选列（竖着切），σ 选行（横着切）。**π 和 σ 别搞反，这是最常见的错**。

### 自然连接 vs 等值连接

- **等值连接**：按条件连接，结果**保留两个表的所有属性**（含重复的）
- **自然连接**：自动按同名属性连接，结果**去掉重复属性**

题目问"结果有几个属性"，自然连接要去重。

## C4 规范化理论 ★★★ L3

### 先搞清四个概念

| 概念 | 定义 |
|:---|:---|
| **函数依赖** X→Y | X 确定 Y，X 相同则 Y 必相同 |
| **部分函数依赖** | X 是组合属性，Y 只依赖 X 的一部分 |
| **传递函数依赖** | X→Y，Y→Z，且 Y 不→X，则 X 传递确定 Z |
| **候选键** | 能唯一确定元组的最小属性集 |

### 四个范式的判定

| 范式 | 条件 | 消除什么 |
|:---|:---|:---|
| **1NF** | 每个属性都是**原子值**（不可再分） | 消除**非原子属性** |
| **2NF** | 满足 1NF，且**非主属性完全依赖于候选键**（不存在部分依赖） | 消除**部分函数依赖** |
| **3NF** | 满足 2NF，且**非主属性不传递依赖于候选键** | 消除**传递函数依赖** |
| **BCNF** | 满足 3NF，且**所有函数依赖的左部都包含候选键** | 消除**主属性对候选键的部分/传递依赖** |

### 判定步骤（照着做）

1. 找候选键（能推出所有属性的最小集合）
2. 分主属性 / 非主属性
3. 看有没有**非原子属性** → 有则不是 1NF
4. 看候选键是不是**组合键**：
   - 是组合键 → 检查非主属性有没有只依赖其中一部分 → 有则不是 2NF
   - 是单属性键 → 一定满足 2NF（因为没有"部分"可言）
5. 看有没有**非主属性依赖非主属性**（传递）→ 有则不是 3NF
6. 看**每个函数依赖的左部是否都含候选键** → 否则不是 BCNF

### 经典例子

`学生(学号, 姓名, 系号, 系主任)`
- 候选键：学号
- 依赖：学号→姓名，学号→系号，系号→系主任
- 学号→系号→系主任，是**传递依赖**
- 结论：满足 2NF，**不满足 3NF**

分解为 3NF：`学生(学号,姓名,系号)` + `系(系号,系主任)`

### 易错点

- **单属性候选键的关系一定满足 2NF**，因为不存在"部分"。
- 判断 3NF 只看**非主属性**之间的依赖，主属性之间的不算。
- BCNF 比 3NF 严，区别在**主属性**是否也有部分/传递依赖。

## C5 SQL 语句 ★★ L2

### 执行顺序（重要）

写的时候是 `SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY`
**实际执行顺序**是 `FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY`

**这解释了为什么 WHERE 里不能用聚合函数**（那时还没分组），而 HAVING 可以。

### 关键语法

```sql
-- 分组过滤
SELECT 系号, AVG(成绩) FROM 学生 GROUP BY 系号 HAVING AVG(成绩) > 80;

-- 连接
SELECT s.姓名, c.课程名 FROM 学生 s JOIN 选修 e ON s.学号 = e.学号 JOIN 课程 c ON e.课程号 = c.课程号;

-- 子查询
SELECT 姓名 FROM 学生 WHERE 学号 IN (SELECT 学号 FROM 选修 WHERE 成绩 > 90);
```

### 易错点

- `WHERE` 过滤行，`HAVING` 过滤组。
- `COUNT(*)` 算所有行，`COUNT(列名)` **不统计 NULL**。
- `DELETE` 删数据（可回滚），`DROP` 删表结构（不可回滚），`TRUNCATE` 清空表（不可回滚但保留结构）。

## C6 并发控制与锁 ★★ L2

### 三种并发问题

| 问题 | 描述 |
|:---|:---|
| **丢失更新** | 两个事务同时读同一数据，后写的覆盖先写的 |
| **脏读** | 读到了别的事务**未提交**的数据 |
| **不可重复读** | 同一事务内两次读同一数据，结果不同（因为别人改了并提交） |

（还有**幻读**：同一事务内两次查询，结果集行数不同。）

### 两级锁

| 锁 | 别名 | 允许 |
|:---|:---|:---|
| **共享锁 S** | 读锁 | 别人可读，不可写 |
| **排他锁 X** | 写锁 | 别人不可读不可写 |

### 两段锁协议（2PL）

- **扩展阶段**：只能加锁，不能解锁
- **收缩阶段**：只能解锁，不能加锁

遵守 2PL 是**可串行化**的充分条件（不是必要条件）。

## C7 完整性约束 ★★ L1

| 约束 | 保证什么 | 例子 |
|:---|:---|:---|
| **实体完整性** | 主键非空且唯一 | PRIMARY KEY |
| **参照完整性** | 外键要么为空，要么引用存在的主键 | FOREIGN KEY |
| **用户定义完整性** | 业务规则 | CHECK(年龄>0) |

## C8 数据仓库与数据挖掘 ★ L1

| | OLTP（操作型） | OLAP（分析型） |
|:---|:---|:---|
| 用途 | 日常交易 | 决策分析 |
| 数据 | 当前、细节 | 历史、汇总 |
| 操作 | 增删改查频繁 | 大量读、批量加载 |
| 设计 | 规范化（3NF） | **反规范化**（星型/雪花） |

**星型模型**：一个事实表 + 多个维度表，维度表不再分解。
**雪花模型**：维度表还可以再规范化分解，层级更多。

**数据挖掘任务**：分类、聚类、关联规则、序列模式、回归。

## C9 分布式数据库 ★ L1

**透明性**（四种）：
- **分片透明**：用户不用管数据分了几片
- **位置透明**：不用管数据在哪台机器
- **复制透明**：不用管副本有几个

## C10 备份与恢复 ★★ L1

| 类型 | 备份什么 | 特点 |
|:---|:---|:---|
| **完全备份** | 全部数据 | 慢、占空间大、恢复最快 |
| **增量备份** | 上次备份后**变化**的数据 | 快、占空间小、**恢复慢**（要逐个叠加） |
| **差量备份** | 上次**完全备份**后变化的数据 | 折中 |

**日志文件的作用**：记录所有更新操作，用于**事务回滚**和**系统故障恢复**。

## C11 数据库设计四阶段 ★★ L2

> **教材 9.7 + 第 12 章，原版本未系统化，2026-10-29 补入**。这是下午场第 2 题的框架。

### 四个阶段

| 阶段 | 产出 | 是否依赖 DBMS |
|:---|:---|:---|
| **1. 需求分析** | 数据字典、数据流图、需求说明书 | 否 |
| **2. 概念结构设计** | **E-R 图** | **否**（独立于任何产品） |
| **3. 逻辑结构设计** | 关系模式（E-R 转表）、规范化 | 部分（关系模型） |
| **4. 物理结构设计** | 索引、存储结构、分区 | **是**（依赖具体 DBMS） |

**关键理解**：**概念设计独立于 DBMS**，这是它存在的意义——让设计不被具体产品绑架，换个数据库不用重做。

### E-R 图集成的三种冲突

多个分 E-R 图合并时会出现：

| 冲突 | 例子 |
|:---|:---|
| **属性冲突** | 同一属性在不同分图中类型不同（一个是 int，一个是 char） |
| **命名冲突** | 同名异义（都叫"编号"但指不同东西）、异名同义（"学号"和"学生号"） |
| **结构冲突** | 同一对象在不同分图中抽象不同（一个当实体，一个当属性） |

### 概念设计的策略

| 策略 | 做法 |
|:---|:---|
| 自顶向下 | 先定全局框架，再逐层细化 |
| **自底向上** | 先做局部 E-R 图，再集成（**最常用**） |
| 混合策略 | 两者结合 |
