# 下午题 03 · UML 图

> 位置：下午场第 3 题（约 15 分）
> 难度：中低。**给场景选图 + 填类图 + 判断关系**，都是套路。

---

## 一、题目长什么样

通常两种形态：

**形态 A：用例图 / 活动图 / 状态图**
1. 给出业务描述，让你**补充图中的参与者或用例**
2. 说明某用例与另一用例的关系（包含 / 扩展 / 泛化）
3. 补全状态图的迁移条件

**形态 B：类图**
1. 补全类名 / 方法名
2. 指出两个类之间的关系（关联 / 聚合 / 组合 / 泛化）
3. 说明为什么用某种关系

---

## 二、六种图的判断（先看题问哪种）

| 题目描述的特征 | 应画的图 |
|:---|:---|
| 系统有哪些功能，谁在用 | **用例图** |
| 业务流程、审批流、并发分支 | **活动图** |
| 一个对象从状态 A 到状态 B | **状态图** |
| 多个对象按时间顺序交互 | **时序图** |
| 类与类的静态结构 | **类图** |
| 系统部署在哪些硬件上 | **部署图** |

### 快速区分活动图 vs 状态图

| | 活动图 | 状态图 |
|:---|:---|:---|
| 主语 | **业务流程** | **一个对象** |
| 节点 | 动作 / 活动 | 状态 |
| 强调 | 步骤顺序、并发 | 状态变迁、事件触发 |

**题干说"订单从待支付到已发货"→ 状态图**（一个对象的状态变化）
**题干说"订单处理流程：先校验库存，再扣款，最后发货"→ 活动图**（流程）

## 三、用例图：参与者与关系

### 参与者（Actor）

- 可以是**人**，也可以是**外部系统**
- 用**小人图标**表示
- 参与者之间可以有**泛化**（如"VIP 用户"继承"普通用户"）

### 用例间三种关系（高频）

| 关系 | 符号 | 含义 | 判断 |
|:---|:---|:---|:---|
| **包含** include | 虚线箭头 + «include» | A 一定用到 B，B 是被提取的公共部分 | "**必须**"、"**每次都**" |
| **扩展** extend | 虚线箭头 + «extend» | B 在特定条件下才补充到 A | "**可选**"、"**如果**"、"**特殊情况**" |
| **泛化** | 空心三角实线 | 子用例是一种父用例 | "**是一种**" |

### 判断口诀

- **一定发生** → 包含
- **可能发生** → 扩展
- **是一种** → 泛化

**例**：
- "用户下单时必须验证身份" → 下单 «include» 验证身份
- "用户下单时如果使用优惠券，则计算折扣" → 下单 «extend» 计算折扣
- "VIP 下单是一种下单" → VIP下单 泛化 下单

### 易错点

- **箭头方向**：包含和扩展的箭头都指向**被包含/被扩展**的用例（即从"主用例"指向"子用例"）。
- 包含是"主 → 子"（主用例依赖子用例），扩展也是"子 → 主"（扩展用例指向主用例）——**这两个方向容易混**。

**准确记法**：
- `A «include» B`：箭头从 A 指向 B（A 用到 B）
- `B «extend» A`：箭头从 B 指向 A（B 扩展 A）

## 四、状态图：三要素

| 元素 | 图形 | 说明 |
|:---|:---|:---|
| **状态** | 圆角矩形 | 对象所处的情况 |
| **迁移** | 箭头 | 状态间的转换 |
| **事件/条件** | 箭头上的文字 | 触发迁移的条件 |

**格式**：`事件[条件]/动作`

**例**：`支付成功[金额足够]/扣减库存`

### 常考：补迁移条件

题目给一个不完整的状态图，问"从 A 到 B 的迁移条件是什么"。

**方法**：回到题干，找"A 变成 B"那句话的触发条件。

## 五、类图：六种关系（核心）

### 关系强度排序

**依赖 < 关联 < 聚合 < 组合 < 泛化 / 实现**

| 关系 | 符号 | 语义 | 判断方法 |
|:---|:---|:---|:---|
| **依赖** | 虚线箭头 `--->` | 临时使用 | 作为**方法参数、局部变量**使用 |
| **关联** | 实线 `——` | 长期结构关系 | 作为**成员变量**持有 |
| **聚合** | 空心菱形 `◇——` | 整体-部分，**部分可独立** | "包含"但可分离 |
| **组合** | 实心菱形 `◆——` | 整体-部分，**同生共死** | "包含"且不可分离 |
| **泛化** | 空心三角实线 `——▷` | is-a 继承 | "是一种" |
| **实现** | 空心三角虚线 `--▷` | 实现接口 | "实现了" |

### 聚合 vs 组合（最常考）

**判断标准：整体消失，部分还在吗？**

| 场景 | 关系 | 理由 |
|:---|:---|:---|
| 班级 — 学生 | **聚合**（空心） | 班级解散，学生还在 |
| 人 — 心脏 | **组合**（实心） | 人死了，心脏不能独立活 |
| 订单 — 订单项 | **组合**（实心） | 订单删除，订单项也没意义 |
| 电脑 — 鼠标 | **聚合**（空心） | 电脑报废，鼠标还能用 |

**记忆**：**空心=松，实心=紧**。菱形永远在**整体**那一端。

### 关联的多重性

| 表示 | 含义 |
|:---|:---|
| `1` | 恰好一个 |
| `0..1` | 零或一个 |
| `*` 或 `0..*` | 零或多个 |
| `1..*` | 一个或多个 |

## 六、答题模板

### 补类名 / 方法名

直接写名字，不要解释：

```
C1：订单
C2：订单项
方法 m1：计算总价()
```

### 判断关系

必须**说明理由**：

> 订单与订单项之间是**组合**关系。
> 理由：订单项不能脱离订单独立存在，订单删除后订单项失去意义，符合同生共死的组合语义。

只写"组合"不给满分，**要写理由**。

### 补用例关系

```
"下单"与"验证身份"是包含关系（«include»），因为每次下单都必须验证身份。
```

## 七、易错点清单

| 错误 | 后果 | 正确做法 |
|:---|:---|:---|
| 聚合和组合搞反 | 扣分 | 问"整体没了，部分还在吗" |
| 菱形画在部分那一端 | 扣分 | 菱形在**整体**端 |
| 包含和扩展方向搞反 | 扣分 | 包含 A→B，扩展 B→A |
| 关系判断不写理由 | 扣一半分 | 必须说明依据 |
| 状态图当活动图 | 全错 | 看主语是"对象"还是"流程" |
| 参与者画成用例 | 全错 | 参与者是**小人**，用例是**椭圆** |

## 八、示例题（自编，非真题）

> 按考点自编，非真题。

**背景**：某电商系统中，一个订单包含多个订单项；订单项记录了商品和数量。订单有"待支付""已支付""已发货""已完成"四种状态。用户下单时必须先验证登录状态；如果用户使用优惠券，则额外执行优惠计算。

**问题**：
1. 订单与订单项是什么关系？说明理由。
2. "下单"与"验证登录"是什么关系？
3. "下单"与"优惠计算"是什么关系？
4. 订单状态从"待支付"到"已支付"的迁移条件是什么？

**参考答案**：

1. **组合**关系。理由：订单项不能脱离订单独立存在，订单被删除后订单项也失去意义，符合同生共死的语义（实心菱形在订单端）。

2. **包含**（«include»）。理由：每次下单都必须验证登录，是被无条件使用的公共行为。

3. **扩展**（«extend»）。理由：只在"用户使用优惠券"这个特定条件下才执行，是可选的补充行为。

4. 迁移条件为"**支付成功**"（事件），可附加条件 `[支付金额 ≥ 应付金额]`。

## 九、练习建议

1. **关系判断**是重点，练到能一眼分清聚合和组合
2. **用例的包含/扩展**要能根据"必须"和"如果"判断
3. 每道题都写出理由，养成习惯——考试时不会忘

**目标**：这道题拿 10 分以上（满分约 15）。
