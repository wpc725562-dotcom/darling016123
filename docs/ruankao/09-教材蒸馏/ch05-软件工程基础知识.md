## 三、核心内容蒸馏

### 5.1 软件工程概述

#### 软件危机

**表现**：软件开发生产率跟不上硬件发展、成本超支、进度延误、质量不可靠、难以维护。

**原因**（教材归纳）：
1. 软件规模越来越大，复杂度急剧上升
2. 缺乏有效的工程化方法
3. 忽视需求分析和文档

**1968 年北约会议**首次提出"软件工程"这个名词——这是常考的"第一次"。

#### 软件工程的定义

教材原文：应用计算机科学、数学及管理科学等原理，以工程化的原则和方法来解决软件问题的工程。

**三个目标**：提高软件生产率、提高软件质量、降低软件成本。

#### 软件工程七条基本原理（Boehm 提出）

教材列了七条，考试偶尔考"以下哪条不是软件工程的基本原则"：

1. 用分阶段的生命周期计划严格管理
2. 坚持进行阶段评审
3. 实行严格的产品控制（基准配置管理）
4. 采用现代程序设计技术
5. 结果应能清楚地审查
6. 开发小组的人员应少而精
7. **承认不断改进软件工程实践的必要性**

### 5.2 软件过程与 CMMI

#### 软件生命周期

**阶段划分**（教材标准划分）：

```
可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 运行维护
```

**各阶段的产出**：

| 阶段 | 产出 |
|:---|:---|
| 可行性研究 | 可行性研究报告 |
| 需求分析 | 需求规格说明书（SRS） |
| 概要设计 | 概要设计说明书（体系结构、接口） |
| 详细设计 | 详细设计说明书（模块内部算法） |
| 编码 | 源代码 |
| 测试 | 测试报告 |
| 维护 | 维护记录 |

#### CMMI 五级（必背）

| 级别 | 名称 | 特征 |
|:---:|:---|:---|
| 1 | **初始级** | 过程混乱，靠个人英雄主义 |
| 2 | **已管理级** | 项目级管理，有基本的计划与跟踪 |
| 3 | **已定义级** | 组织级标准过程，项目按裁剪使用 |
| 4 | **量化管理级** | 用数据量化管理过程 |
| 5 | **优化级** | 持续改进过程 |

**记忆口诀**：**初管定量优**

### 5.3 软件过程模型（★★★ 必考）

#### 六种模型的对比

| 模型 | 特征词 | 适用场景 | 缺点 |
|:---|:---|:---|:---|
| **瀑布** | 阶段严格顺序、文档驱动、不可回溯 | 需求**明确且稳定** | 后期才发现问题，成本高 |
| **原型** | 快速构建可运行版本给用户看 | 需求**不明确** | 原型可能被误当产品 |
| **螺旋** | 螺旋上升，**每个循环含风险分析** | **风险大**的大型项目 | 成本高，需风险评估能力 |
| **增量** | 分批交付，每批可用 | 可分块上线 | 需要良好的架构规划 |
| **敏捷** | 迭代、拥抱变化、可工作软件优于文档 | 需求**变化快** | 文档少，依赖团队能力 |
| **V 模型** | 瀑布变体，**测试与开发阶段一一对应** | 强调测试的项目 | 同瀑布 |

#### 判断口诀（考场上直接用）

- 看到"**需求不明确**"→ **原型**
- 看到"**风险大**"、"风险分析"→ **螺旋**
- 看到"**需求稳定、文档驱动**"→ **瀑布**
- 看到"**分批交付**"→ **增量**
- 看到"**拥抱变化、迭代**"→ **敏捷**

#### 螺旋模型的四个象限（教材重点）

每个螺旋循环包含四个活动：
1. **制定计划**（确定目标、方案、约束）
2. **风险分析**（评估方案、识别风险、解决风险）
3. **实施工程**（开发、验证）
4. **客户评估**（评审、提出修改）

**核心是风险分析**——这是螺旋模型区别于其他模型的根本特征。

#### V 模型的对应关系（常考）

| 开发阶段 | 对应测试阶段 |
|:---|:---|
| 需求分析 | **验收测试** |
| 概要设计 | **集成测试** |
| 详细设计 | **单元测试** |
| 编码 | （被测对象） |

**考题形式**："概要设计对应哪种测试？" → 集成测试。

#### 敏捷开发的核心价值观（教材列了四条）

1. **个体和互动** 高于 流程和工具
2. **可工作的软件** 高于 详尽的文档
3. **客户合作** 高于 合同谈判
4. **响应变化** 高于 遵循计划

**注意**：是"高于"不是"取代"。敏捷不是不要文档，是文档的价值低于可运行的软件。

### 5.4 需求分析

#### 需求的分类

| 类型 | 内容 |
|:---|:---|
| **功能需求** | 系统必须做什么 |
| **非功能需求** | 性能、可靠性、安全性、可维护性等 |
| **设计约束** | 技术选型、平台限制 |

#### 需求获取的方法

访谈、问卷、观察、原型、联合应用开发（JAD）、文档分析。

#### 需求分析的原则

1. 必须理解并描述问题的信息域
2. 必须定义软件应完成的功能
3. 必须描述作为外部事件结果的软件行为
4. 必须对描述信息、功能和行为的模型进行分解

### 5.5 系统设计

#### 概要设计 vs 详细设计

| | 概要设计 | 详细设计 |
|:---|:---|:---|
| 关注 | 系统**体系结构**、模块划分、接口 | **模块内部**的算法与数据结构 |
| 产出 | 概要设计说明书 | 详细设计说明书 |
| 方法 | 结构化设计、面向对象设计 | 流程图、伪代码、PDL |

#### 内聚与耦合（★★★ 必考）

**目标**：**高内聚、低耦合**。

##### 内聚：从低到高（越高越好）

| 等级 | 名称 | 特征 |
|:---:|:---|:---|
| 1（最低） | **偶然内聚** | 模块内各部分毫无关系 |
| 2 | **逻辑内聚** | 由参数决定执行哪个逻辑（如一个"输出"模块能输出各种报表） |
| 3 | **时间内聚** | 需要在同一时间段执行（如初始化模块） |
| 4 | **过程内聚** | 必须按特定次序执行 |
| 5 | **通信内聚** | 操作同一数据结构 |
| 6 | **顺序内聚** | 一部分的输出是另一部分的输入 |
| 7（最高） | **功能内聚** | 所有部分共同完成**一个**功能 |

**记忆口诀**：**偶逻时过通顺功**

##### 耦合：从低到高（越低越好）

| 等级 | 名称 | 特征 |
|:---:|:---|:---|
| 1（最低） | **非直接耦合** | 模块间无直接联系 |
| 2 | **数据耦合** | 只传简单数据参数（如 `int age`） |
| 3 | **标记耦合** | 传整个数据结构（如整个 `Student` 对象） |
| 4 | **控制耦合** | 传控制信息（如开关量、标志位） |
| 5 | **外部耦合** | 依赖外部环境（如共享外部文件格式） |
| 6 | **公共耦合** | 共享全局数据区 |
| 7（最高） | **内容耦合** | 直接访问另一模块内部数据或代码 |

**判断技巧**：
- 传 `int`、`String` → **数据耦合**
- 传整个对象/结构体 → **标记耦合**
- 传了一个 if/switch 的判断条件 → **控制耦合**
- 用了 `global` 变量 → **公共耦合**
- 直接改别人的私有成员 → **内容耦合**

### 5.6 软件测试（★★★）

#### 黑盒测试（不看代码，看功能）

| 方法 | 怎么用 |
|:---|:---|
| **等价类划分** | 把输入分成有效/无效等价类，每类取一个代表 |
| **边界值分析** | 取边界及其两侧（如 [1,100] 取 0,1,100,101） |
| **因果图** | 输入条件与输出结果的逻辑组合 |
| **错误推测** | 凭经验猜哪里容易错 |

**边界值分析是等价类划分的补充**：大量错误发生在边界上，所以边界要单独测。

#### 白盒测试（看代码结构）

| 覆盖准则 | 强度 | 说明 |
|:---|:---:|:---|
| **语句覆盖** | 最弱 | 每行代码至少执行一次 |
| **判定覆盖**（分支覆盖） | ↑ | 每个判断的真假都出现 |
| **条件覆盖** | ↑ | 每个条件的真假都出现 |
| **判定/条件覆盖** | ↑ | 同时满足判定和条件覆盖 |
| **条件组合覆盖** | ↑ | 每个判断中条件的所有组合 |
| **路径覆盖** | 最强 | 所有可能路径 |

**记忆**：语句 < 判定 < 条件 < 判定/条件 < 条件组合 < 路径

**关键辨析**（高频）：
- **语句覆盖不能保证判定覆盖**：可能只走了判断为真的分支
- **条件覆盖不一定满足判定覆盖**：可能每个条件都取了真假，但判断结果没取全
- 所以才有"判定/条件覆盖"这个折中准则

#### 测试阶段与对应关系

| 测试 | 对象 | 依据 | 谁做 |
|:---|:---|:---|:---|
| **单元测试** | 单个模块 | 详细设计 | 开发人员 |
| **集成测试** | 模块间接口 | 概要设计 | 开发人员 |
| **系统测试** | 整个系统 | 需求规格 | 测试人员 |
| **验收测试** | 用户视角 | 用户需求 | 用户 |

**集成测试的两种策略**：
- **自顶向下**：需要桩模块（stub）模拟下层
- **自底向上**：需要驱动模块（driver）模拟上层

**记忆**：自顶向下要**桩**（stub，替身），自底向上要**驱动**（driver，调用者）。

#### 回归测试

修改代码后，重新运行之前的测试，确保没引入新问题。

### 5.7 软件维护

#### 四种维护类型（必考占比）

| 类型 | 目的 | 占比 |
|:---|:---|:---:|
| **正确性维护** | 改正 bug | 约 20% |
| **适应性维护** | 适应外部环境变化（新 OS、新硬件） | 约 25% |
| **完善性维护** | **增加新功能、提升性能** | **约 50%（最大）** |
| **预防性维护** | 为将来可维护性做改造 | 约 5% |

**必记**：**完善性维护占比最大**。这个反直觉——很多人以为改 bug 最多，实际上加功能最多。

#### 可维护性的度量

可理解性、可测试性、可修改性、可靠性、可移植性、可使用性、效率。

### 5.8 软件项目管理（★★★）

#### 进度管理：甘特图 vs PERT

| | 甘特图 | PERT 图 |
|:---|:---|:---|
| 形式 | 横道图，时间轴 | 网络图（节点 + 箭线） |
| 强项 | **直观展示进度** | **展示依赖关系**、算关键路径 |
| 弱项 | 看不出依赖 | 不直观 |

#### 关键路径（必考计算）

**步骤**：
1. 画出网络图
2. 列出所有从起点到终点的路径
3. 每条路径工期相加
4. **最长的路径 = 关键路径**，其长度 = **最短工期**

**关键性质**：
- 关键路径上的活动**总时差为 0**
- 关键路径**可能不唯一**
- 缩短工期必须缩短关键路径上的活动

**总时差** = 最晚开始 − 最早开始 = 最晚完成 − 最早完成

**例**：

| 活动 | 前置 | 工期 |
|:---|:---|:---:|
| A | — | 3 |
| B | A | 4 |
| C | A | 2 |
| D | B,C | 5 |

路径：
- A→B→D = 3+4+5 = 12
- A→C→D = 3+2+5 = 10

关键路径 **A→B→D**，最短工期 **12**

**易错点**：关键路径是**最长**路径，不是最短。很多人直觉选最短。

#### 风险管理

**过程**：风险识别 → 风险预测（概率 + 影响）→ 风险应对计划 → 风险监控

**四种应对策略**：

| 策略 | 做法 | 例子 |
|:---|:---|:---|
| **回避** | 改变计划，绕开风险 | 不用不成熟的技术 |
| **转移** | 把风险转给第三方 | 买保险、外包 |
| **减轻** | 降低概率或影响 | 做原型验证、加冗余 |
| **接受** | 认了，准备应急储备 | 留缓冲时间 |

#### 配置管理

**配置项**：需要版本控制的所有产出（代码、文档、数据）。

**配置管理活动**：
1. **配置标识**（给每个配置项编号）
2. **版本控制**
3. **变更控制**（变更申请 → 评估 → 批准 → 实施 → 验证）
4. **配置审计**（确保实际与记录一致）
5. **状态报告**

**基线（baseline）**：经过评审、被正式确认的配置项集合。**基线一旦建立，修改必须走变更控制流程**。

#### 质量管理

**质量保证（QA）** vs **质量控制（QC）**：
- QA：**过程导向**，确保过程正确（预防）
- QC：**产品导向**，检查产品是否合格（检测）

## 四、教材强调但容易忽略的

1. **敏捷是"高于"不是"取代"**：可工作软件高于详尽文档，不等于不要文档。

2. **螺旋模型的核心是风险分析**，四个象限里"风险分析"是它的标志。看到"风险"就选螺旋。

3. **语句覆盖不能保证判定覆盖**，这是白盒测试最常考的辨析点。

4. **完善性维护占比最大（50%）**，不是正确性维护。这个反直觉。

5. **自顶向下集成要桩，自底向上要驱动**。stub 和 driver 经常被搞反。

6. **关键路径是最长路径**，长度等于最短工期。

7. **QA 是过程，QC 是产品**。预防 vs 检测。
