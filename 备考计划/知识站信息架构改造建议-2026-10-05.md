### 2.1 `squidfunk/mkdocs-material` 27.5k —— 标签体系与「构建期插件」的完整答案

**① 怎么做的**：它把「横向聚合」拆成 4 个独立插件，各管一段：

| 插件 | 管什么 |
|:--|:--|
| **meta** | 目录级打标（`.meta.yml` 递归向下继承） |
| **tags** | 扫描标签 → 建倒排索引 → 渲染标签索引页 → 导出 `tags.json` |
| **search** | 索引里带 boost / exclude |
| **blog** | archive / categories / authors / pagination |

**② 关键字段（都是文档原文）**

*tags 插件四层能力：*
1. 页面 frontmatter `tags:`（字符串列表，允许空格）
2. **目录级打标** —— 严格说属于 **meta 插件**：目录放 `.meta.yml`，内容 `tags: [Example]`，**递归合并到该目录及所有子目录的页面**；「列表和字典递归合并」
3. **标签索引页** —— 页面里写 `<!-- material/tags -->` 即渲染成索引（9.6.0 起弃用了旧的 `tags_file`）；支持 `scope: true`（只列当前子章节的标签）、`include` / `exclude`、`listings_map` 复用预设
4. **搜索可发现** —— 文档只有一句「make them discoverable via search and dedicated tags indexes」，**没有细节**（别指望它）

*三项进阶：*
- `tags_hierarchy: true`（9.7.0，实验性）⇒ 写 `科目/题型` 渲染成父子结构；分隔符 `tags_hierarchy_separator`（默认 `/`）
- **shadow tags**（5 个配置：`shadow` / `shadow_on_serve` / `shadow_tags` / `shadow_tags_prefix` / `shadow_tags_suffix`）⇒ 一组「只用于组织、默认不渲染」的标签
- **`tags_allowed`（受控词表）** ⇒ 标签必须命中白名单，**否则直接停构建**（stops the build）

*search 插件：*
- `search.boost` 写在 **frontmatter**（`search: { boost: 2 }`，也可 `0.5` 降权）
- `search.exclude: true` 整页排除；`data-search-exclude` 可精确到**某个 section 或某个 block**
- `search.suggest` / `search.highlight` / `search.share`

*navigation（十件套，全部实测字段）：*
`navigation.instant`（SPA 化）· `.instant.prefetch` · `.instant.progress` · `navigation.tracking`（地址栏跟随锚点）· `navigation.tabs` · `tabs.sticky` · `navigation.sections` · `navigation.expand` · **`navigation.path`（面包屑，9.7.0）** · `navigation.prune`（**构建体积 -33%+**）· `navigation.indexes`（section index 页）· `toc.follow` · `toc.integrate` · `navigation.top`；另有 frontmatter `hide: [navigation, toc, path]`

*blog 插件：*
`archive`（`archive_url_format` / `archive_pagination_per_page` / `archive_toc`）· `categories`（`categories_allowed` **也是受控词表** / `categories_url_format` / `categories_slugify`）· `authors`（`authors_file` / `authors_profiles_url_format`）· `pagination`（`pagination_per_page`）· frontmatter `draft` / `pin` / `readtime` / `date`

**③ 对本站的映射**
- `tags_allowed` ⇒ **我们要做的「受控词表」应该做成硬失败**，不是 warning
- meta 的 `.meta.yml` ⇒ **目录级打标的现成思路**：`docs/posts/english/**` 全量补 `公共英语`，不必逐页写
- `search.boost` ⇒ 本站的「学习手册 ⭐」这类页面**应该被搜索加权**（现在纯靠标题权重 4）
- `navigation.path` ⇒ 面包屑，本站完全没有
- `navigation.prune` ⇒ 404 页规模下**值得实测**构建体积
- `data-search-exclude` ⇒ 我们的「章节审计报告」「备份目录」这类内部产物，可以**精确到段落**排除

**④ 不能照抄**：它是 **Python 构建期插件**。VitePress 没有插件生态等价物 —— 上面每一条「生成标签页 / 目录级打标 / 搜索注入」都**必须在 Node 侧自己写脚本**（`transformPageData` 或独立 `.mjs`）。照抄概念，不能照抄实现。

### 2.2 `adityatelange/hugo-PaperMod` 14.0k —— 把「导航之外的路」做全

**① 怎么做的**：README 的功能清单里，有 4 条正好是本站缺的横向路径：

| 能力 | 它怎么做 |
|:--|:--|
| **Breadcrumb navigation** | 页面顶部面包屑 |
| **Post archives and taxonomies** | Hugo taxonomies 机制：**一个 taxonomy 自动生成一个列表页，每个 term 自动生成一个详情页** |
| **Related post suggestions** | 文末「相关文章」 |
| **Fuse.js 客户端搜索** | 零后端全文搜索 |

另：三种布局（Regular / Home-Info / Profile）· OG+Twitter+Schema.org · cover images · TOC · 多作者 · 代码复制按钮 · **零 JS 构建依赖**

**② 关键字段**：Hugo 的 taxonomies 在 `hugo.toml` 里声明（如 `taxonomies: { tag: tags, category: categories }`），页面 frontmatter 写 `tags: [...]` 即自动入索引。**不需要逐页注册**。

**③ 对本站的映射**
- **分类法（taxonomy）= 标签体系**。Hugo 的「一个 taxonomy 一套自动页」就是我们要的 `/tags/` + `/tags/<tag>/`
- **面包屑**：本站没有。404 页规模下，「我在哪一层」的迷失是真实存在的
- **相关文章**：本站也没有。现在的「读完往哪走」只有侧边栏和搜索两条路

**④ 不能照抄**：Hugo 的 taxonomy 是**构建器原生**能力，VitePress 完全没有 —— 又要自己写脚本生成页。**「相关文章」更要注意**：它需要相似度算法（Hugo 用 tag 交集 + 日期），我们 tags 还没收敛，**先做标签再做相关文章**，否则相关性会很差。

### 2.3 `timlrx/tailwind-nextjs-starter-blog` 10.6k —— 「系列」不新造概念

**① 怎么做的**
- **每个唯一 tag 独立成路由** `/tags/[tag]`；列表页带 **tag 侧边栏**（`ListLayoutWithTags`）
- 搜索是 **Kbar 命令面板**（不是输入框弹窗）
- **3 种 post layout**（`PostLayout` / `PostSimple` / `PostBanner`）+ **2 种 list layout**
- **多部分文章用嵌套路由**：`/blog/nested-route/...` —— **不新造「系列」概念**
- RSS + sitemap 开箱即用
- frontmatter：`title` `date` `tags` `lastmod` `draft` `summary` `images` `authors` `layout` `canonicalUrl`
- 内容与配置分离：`data/siteMetadata` · `data/authors/` · `data/projectsData` · `data/headerNavLinks` · `data/blog`

**② 关键字段**：`layout` 是**页面级**的（每篇自己选布局）；`headerNavLinks` 是**数据文件**（导航不写在配置逻辑里）。

**③ 对本站的映射（这条最有价值）**
- 本站的日语有**三条并行线**（深度笔记 / 跟课笔记 / 同步手册），覆盖**同一本书的同一批课次**。
  它证明：**同一内容的多部分，用「路径层级 + 一个切换」表达，比三个并列导航项清楚**
- `data/headerNavLinks` ⇒ **导航应该抽成数据文件**，而不是埋在 1401 行配置中间
- `layout` 页面级 ⇒ 本站的「学习手册 / 真题 / 笔记」**应该用 layout 区分版式**，而不是全靠正文自律

**④ 不能照抄**：Kbar 是 React 组件，VitePress 没有等价物（要用 Vue 重写，成本不低）。RSS 要自己接插件。

### 2.4 `withastro/starlight` 9.4k —— 「元信息写在页面身上」

**① 怎么做的**：sidebar **默认从文件系统结构自动生成**（`src/content/docs/` 目录树），也可显式 `autogenerate: { directory, collapsed }`。**排序按文件名**。

**② 关键字段（TypeScript 类型原文）**
```ts
type SidebarItem =
  | string
  | ({ translations?: Record<string,string>; badge?: string | BadgeConfig } & (
      | { link: string; label: string; attrs?: ... }     // 外链
      | { slug: string; label?: string; attrs?: ... }    // 内链，label 默认取页面 title
      | { label: string; items: SidebarItem[]; collapsed?: boolean }  // 分组
    ))
  | { autogenerate: { directory: string; collapsed?: boolean; attrs?: ... } }

interface BadgeConfig { text: string; variant?: 'note'|'tip'|'caution'|'danger'|'success'|'default'; class?: string }
```
另：`editLink: { baseUrl }` · `lastUpdated` · `pagination` · `tableOfContents: { minHeadingLevel, maxHeadingLevel }` · **搜索用 Pagefind**（可配 `pagefind.ranking` / `indexWeight` / `mergeIndex`）· `locales` / `i18nLoader` · 组件可整体覆盖（`components`）

**③ 对本站的映射（这条直接解掉最大负债）**
- **排序权与徽章属于页面** ⇒ `config.mts` 的 1401 行里，**排序和 ⭐/⚠️ 标记可以搬进 frontmatter**
- 本站现在把徽章塞在 nav 的 `text` 里 —— 例如 `'📖 学习手册 ⭐'`、`'📖 同步手册 · 浓缩（每课 4 行）⚠️ 中高级语法点待修正'`。
  **这正是 Starlight 用 `badge` 解决的问题**：徽章是结构化字段（有 variant 配色），不是文本里的一颗星
- `autogenerate` ⇒ 「目录进哪一组」写在配置，**「目录里有什么」由文件系统决定**

**④ 不能照抄**：Starlight 是 Astro 集成，**换框架不现实**。抄的是**设计原则**（元信息下沉到页面），实现要自己在 VitePress 里写生成脚本。

### 2.5 `redblobgames.com` —— 按「成熟度」分区，而非按学科

**① 怎么做的**
- 顶层三大**动词**分区：**Learn**（成体系的交互式教程）· **Play**（边学边做的 demo）· **Ponder**（尚未成体系的想法）
  ⇒ 本质是**按内容成熟度分级，不是按学科分类**
- 板块内是**卡片列表**（缩略图 + 标题 + 链接 + `Also:` 概念软标签）
- 常见**成对结构**：「主文章 + implementation guide」
- 真实分类**藏在 URL 路径**里：`/pathfinding/` `/grids/` `/maps/` `/articles/` `/making-of/` `/x/`
- 没有独立标签页、没有显式学习路径 —— **靠排列顺序暗示由浅入深**

**② 关键字段**：无（静态站）。核心是**分区命名**与**卡片策展**。

**③ 对本站的映射**
- 本站的 `0基础 / 刷题 / 高频考点` 就是**用途维度**，和 `Learn / Play / Ponder` 同构 ——
  说明**「按用途分区」是成立的**，只是不该和「按科目分区」平铺在同一层导航
- `Also:` 软标签 ⇒ 我们的 tags 应该**在文末露出**（现在 tags 完全不可见）
- 「教程 + 实现指南」成对 ⇒ 我们的「**学习手册 + 专项题库**」就是同一模式，应该成对出现

**④ 不能照抄**：它是**手工策展**的单人站，规模远小于我们（我们 404 页）。手工策展在 404 页规模下**维护不动** —— 这恰恰是我们要标签体系的理由。

### 【可选 1】搜索加「只搜本科目」过滤 🟡 **做了半条（boost，非 filter）**

VitePress **无原生板块过滤**，但有两条已核实的路径：
- `miniSearch.searchOptions.filter` —— 文档 ID 是**站点相对路径**（如 `/guide/page.html#section`，**不含 base**）⇒ 可按前缀过滤；
- `options._render` —— 可按路径整块排除（`if (env.relativePath.startsWith('some/path')) return ''`）。

**原做法**：自定义 `SearchBox` 组件，加「本科目 / 全站」开关，把当前路由前缀传进 `filter`。
**成本**：3–4h · **收益**：404 页规模下，「搜『极限』出来一堆日语和雅思」是真实噪声。**但痛感还没到，可等。**

**实际做法（更轻、零破坏）**：不做「硬过滤」，改做 **`boostDocument` 加权**——
```ts
miniSearch: { searchOptions: { boostDocument(id) {
  const here = decodeURIComponent(location.pathname)
  const m = here.match(/^\/([^/]+)\/([^/]+)\//)          // 取当前分区的两段前缀
  if (!m) return 1
  return id.startsWith(`/${m[1]}/${m[2]}/`) ? 1.5 : 1     // 同分区结果排前
} } },
```
**为什么改路线**：`boostDocument` 是**纯排序调整**，不会把跨科结果整块藏起来（读者搜「极限」时
其实**需要**看到日语里同名概念）；而自定义 `SearchBox` 要 fork 主题组件、维护搜索 UI 状态，
**收益/风险比明显更差**。痛点真到那天，再上 filter 开关不迟。

## 六、四条提醒

**① 别拿做工具替代做正事。**（看板里专门警告过）
上面只有 **P0 两条 + P1 导航重组**是「不做会持续硌脚」的；标签体系（P1）值得做，是因为**数据已经在了**（224 页），属于捡现成的。sidebar 脚本化（P2）现在孤页 0 个，是「为未来买保险」，不急。

**② 参照物只抄设计原则，别抄实现。**
六个参照物**没有一个**能和 VitePress 直接互换 —— mkdocs 是 Python 插件、PaperMod 是 Hugo、tailwind 是 React、Starlight 是 Astro、redblobgames 是手工策展、distill 是内容形态。
能抄的是：**「受控词表要硬失败」（mkdocs）· 「排序权属于页面」（Starlight）· 「系列不新造概念」（tailwind）· 「按用途分区成立」（redblobgames）· 「类型徽章 + 时间流」（distill / 阮一峰）**。
⚠️ 还有一条**反向**的：**「别照抄实现」也要具体到某一行** —— 比如 tailwind 的「每标签一页」在本站就不该抄（39 个路由会全落进孤立页黄灯）。

**③ ★ 「检查器说没问题」不等于没问题 —— 别让生成器和检查器共享同一个错误假设。**
本批实测事故：新建的 `/tags/` 与 `/updates/` 两页链到了 **11 个被 `srcExclude` 排除的页面**，
构建报 **31 处 dead link**；而 `check-links.mjs` 打印「✅ 无死链」。
根因是**两个洞正好互相掩盖**：
- **生成器**（`gen-tags` / `gen-updates`）遍历 `docs/**/*.md` 时**没读 `srcExclude`**；
- **检查器**（`check-links`）只有「config 的 `link:`」那一段套了 `srcExclude`，**正文链接那一段一直没套**。

⇒ 处置：抽出 **`scripts/src-exclude.mjs`** 作为 srcExclude 的**唯一解析入口**（4 个脚本各写一份 = 必然漂移），
生成器跳过被排除页、检查器把「目标被排除」报成死链。
> 附带挖出一个更阴的：解析 `srcExclude` 时**会把块内 `//` 注释里的示例路径当成真规则** ——

**④ ★ 检查器要跑在「机器会自动跑的地方」，不是文档里、也不是一条手动命令里。**
本批的元教训：`home:stats:check` 的逻辑**一直是对的**，只是**没人跑**，首页两处篇数就烂了半个月。
于是先做了 `check:all`（11 个检查器收敛成一条命令）—— 但这**还没完**：命令本身仍然靠人记得敲，
只是把「记得跑 11 个」换成「记得跑 1 个」。真正的闭环是接进 `auto-patrol.yml`（每天 3:00 自动跑），
并把**触发路径**收敛成 `scripts/**`（原先逐个列脚本，本批新加的 8 个检查器**全没覆盖** ⇒ 改了它们 CI 无反馈）。
⇒ **一条纪律只有落到调度器上才算成立**；写在文档里、或只做成一条手动命令，都只是「更体面的遗忘」。
