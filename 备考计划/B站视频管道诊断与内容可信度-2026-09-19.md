## 1. 复核性能部分

### 1.1 已有专文覆盖了什么（不重复）

`docs/guide/bili-subtitle-pipeline-perf.md` 已经完整分析并给出了结论：

| 瓶颈 | 量级 | 状态 |
|:---|:---|:---|
| ① 没有输出校验 → 68% 数据是错的 | 浪费 ≈41 分钟 | ✅ 已加 `aid+cid` 校验 |
| ② 重试尾巴（拿不到轨的分P 跑满 40 次） | 占难命中视频 **88–98%** 耗时 | ✅ 已提供 12 次 + 去睡 → **11x** |
| ③ 每请求新建 TLS 连接 | 单请求 **26%**（110.3ms → 复用 81.8ms） | ⬜ 未做 |
| ④ 并发度只有 6 | 尾巴上 **1.5x** | ⬜ 未做 |
| ⑤ 无负缓存 | 每轮重复浪费 | ⬜ 未做 |
| ⑥ `--force` 无断点续传 | 中断即全废 | ✅ 已加 `--refresh` |

**它的核心判断我完全同意，而且值得引用**：

> **这套链路的效率损失主要不是「跑得慢」，而是「跑得快但跑错了」。**
> **修正确性花了 41 分钟；修速度（11x）只省了 6 分钟。顺序不能反。**

→ **所以"换一个更快的工具"是答错题。** 这个管道的问题从来不是速度。

### 1.2 ★ 本文最重要的发现：优化做了，但默认值没改

**已有专文写「✅ 已降到 12 次 + 去睡 → 11x」。但我读代码发现：**

## 2. 替代方案评估

### 2.1 先说结论：瓶颈不在客户端

darling 的直觉是"工具落后 → 换一个"。但瓶颈链条是：

```
慢  ←  重试尾巴（参数问题，已可解，12x）
    ←  B站 API 有 68% 概率返回别的视频的字幕轨（服务端行为）
    ←  拿不到字幕只能走 ASR（本质成本）
```

**中间那一环是 B 站服务端的行为。换任何 HTTP 客户端、任何封装库，这个 68% 都在那里，一样要重试。**

### 2.2 候选方案对比

| 方案 | 能解决瓶颈吗 | 会丢掉什么 | 结论 |
|:---|:---|:---|:--:|
| **现管道 + 显式传参** | ✅ 12 倍 | 无 | ✅ **推荐（改动量 = 0 行代码）** |
| `asyncio` + `aiohttp` | ⚠️ 理论更高并发 | 无（但要重写抓取层） | ⚠️ 已有专文列为 P3，收益未验 |
| `bilibili-api-python` | ❌ 同源问题 | **`aid+cid` 校验 + `cos/ov` 内容校验** | ❌ 不推荐 |
| `yt-dlp` | ❌ | 上述全部 + 要自己处理 wbi 签名 | ❌ 不推荐 |
| `BBDown` | ❌ | 上述全部；**且上游已 archived（2026-05-14）** | ❌ 不推荐 |
| `httpx.Client` 连接池 | ✅ 解决瓶颈③（26%） | 无（可叠加） | ⚠️ 可作补丁 |

> `yt-dlp` 在**"把视频下下来"**这个任务上确实更好（见 skill `bilibili-video-capture` 的实测：3.58 MiB 音频 3 秒）。
> **但本项目要的不是"下载视频"，是"带校验的字幕库"。** 任务不同，答案不同。

### 2.3 换工具会失去什么（重点）

**`aid+cid` 不变量校验是整个管道里最值钱的一行逻辑**（`bili_analyze.py:257-267`）：

```python
# ★ 核心判据：正确轨的路径里含 aid+cid
aid, real_cid = data.get("aid"), data.get("cid")
key = ("%s%s" % (aid, real_cid)) if (aid and real_cid) else None
if key:
    matched = [s for s in subs if key in (s.get("subtitle_url") or "")]
```

**为什么不可替代**：B 站返回的错误字幕轨，`code` 恒为 0、`lan` 恒为 `ai-zh`、`is_lock: false`、格式完全合法
—— **从响应本身完全看不出异常**，只有下载下来读内容才发现。

任何现成库都不做这个校验。它们会**静默地**把"火锅探店""日本世田谷灭门案"的字幕
当成"计算机课程"存下来（这两个都是本项目实际抓到的案例）。

→ **换了工具，darling 的第四个担忧（内容真实性）就失去了唯一的自动化防线。**

## 3. 内容可信度验证体系

### 3.1 风险是真实的 —— 有实证

我在 `data/bili-analyze/BV1husGzwEtZ/subtitle_p105.txt`（计算机课程，53 字节）里读到的内容是：

```

```

**这不是计算机课。** 它被当成计算机课程的字幕存了下来。

已有专文记录的另一个案例：`BV1husGzwEtZ` P1 标题是「1.1函数的定义和定义域」，
内容是**日本世田谷灭门案**。

### 3.2 已有机制：三层校验（做得很好）

| 层 | 机制 | 产物 | 状态 |
|:--|:---|:---|:--:|
| **L1** | **URL 不变量**：正确轨路径含 `prod/{aid}{cid}{hash}` | `_verify.jsonl` | ✅ |
| **L2** | **内容一致性**：与同视频其他分P 比余弦相似度 `cos` + 词汇重叠 `ov` | `_verify2.jsonl` | ✅ |
| **L3** | 人工抽查 | 无固定产物 | ⚠️ 偶发 |

**L2 的实测效果（我做的闭环验证）** —— 我手工发现的可疑文件，机制**全部自动判出**：

```json
{"p":105,"ok":false,"cos":0.1618,"ov":0,"verdict":"junk"}   ← 「我做保安也是因为这个」
{"p":74, "ok":false,"cos":0.1618,"ov":0,"verdict":"junk"}
{"p":80, "ok":false,"cos":0,     "ov":0,"verdict":"junk"}
{"p":124,"ok":false,"cos":0.0772,"ov":0,"verdict":"junk"}
```

→ **机制有效，能自动抓到人工才能发现的问题。**

**另一个重要设计**（`bili_filter_units.py` docstring）：
> `_verify.jsonl` 的 `ok:false` **不等于内容错** —— 实测 `BV1X4411J792` 的 P58/P60/P62 内容与该分P标题完全对应，却因 URL 没匹配上不变量而被标 false。只按 `_verify.jsonl` 过滤会**误删约 19 个正确分P**。

→ 所以 `_verify2` 优先。**这是"宁可放过、不可错杀"的正确取舍。**

### 3.4 建议补两层（L4 / L5）

现有 L1/L2 解决的是"**这段字幕是不是这个视频的**"。但 darling 的担忧还有一半没覆盖：

> 即使字幕是对的，**UP 主讲的内容本身可能错**；即使 UP 主讲对了，**AI 提炼成考点时可能走形**。

| 层 | 验什么 | 怎么验 | 判定标准 |
|:--|:---|:---|:---|
| **L4 · 主题一致性** | 分P 内容 vs **分P 标题** | 用已存在的 `_part_titles_all.json`（148 KB）与字幕做关键词比对 | 标题关键词命中率 <30% → 标记可疑 |
| **L5 · 权威交叉** | 提炼的考点 vs **课本/真题** | 每个考点标注「课本页码」或「真题年份题号」 | **无出处的考点不许进讲义** |

**L5 是治本的那一层。** 项目在 C 语言上**已经做到了**（`textbook.mjs` + "标准答案必须有 gcc 凭据"），
但高数、政治、英语**还没有**。

### 3.5 AI 生成内容的验证方法（分科）

| 科目 | 验证手段 | 可自动化 | 现状 |
|:---|:---|:--:|:---|
| **C 语言 / 数据结构** | **gcc 实测**（最硬） | ✅ | ✅ 已立铁律 |
| **高等数学** | ① 数值回代 ② **SymPy 符号验证** ③ 双源交叉 | ✅ | ⚠️ 只有 node 数值表 |
| **英语** | 官方答案核对；语法点查语法书 | ⚠️ 部分 | ❌ 无 |
| **政治** | **官方考纲 + 指定教材**（唯一权威） | ❌ | ❌ 无 |

**给高数补一条最具体的建议**：装 `sympy`，给高数配一个"gcc"。

```python
import sympy as sp
x = sp.Symbol('x')
sp.limit(sp.sin(x)/x, x, 0)                          # → 1
sp.limit(1/x, x, 0, '-')                             # → -oo（左极限）
sp.limit(1/x, x, 0, '+')                             # → oo （右极限）
sp.diff(x**2, x)                                     # → 2*x
sp.integrate(sp.exp(-x**2), (x, -sp.oo, sp.oo))      # → sqrt(pi)
```

**成本极低、收益极高** —— 高数最大的问题是"没有编译器、无法取证"，
SymPy 正好补上这个洞。`〔待安装验证〕`

### 3.6 通用规则：证据等级标注

任何 AI 生成的结论，进讲义前必须标级：

| 等级 | 标记 | 判据 | 例子 |
|:---|:---|:---|:---|
| 实测 | `〔实测〕` | 有 gcc / SymPy / 官方答案凭据 | "`printf("<%5d>",7)` 输出 `<    7>`（gcc 实测）" |
| 推断 | `〔推断〕` | 有依据无直接凭据 | "该考点 3 年出现 2 次，倾向重点" |
| 假设 | `〔假设〕` | 待验证 | "政治背诵为主" |
| **待查** | `〔待查〕` | **无任何凭据** | ❌ **不允许进讲义** |

| 未抽取题目 | 字幕里有大量真题（"这是 24 年四川的题"），没抽出来 |
| 未与 `历年真题/` 交叉 | 无法验证"UP 主讲的考频"是否属实 |

#### 4.2.1 ✅ junk 污染核对：**干净**

把 `_extract/` 全部 md 的「出处」行解析出来（正则抓 `P\d+`），逐条比对对应 BV 的 `_verify2.jsonl`：

| 指标 | 结果 |
|:---|:--:|
| 提取产出文件数 | **53 份** |
| 引用分P 总数 | **754 处** |
| 其中 **junk** | **0 处** ✅ |
| 其中**无校验记录** | **0 处** ✅ |
| 涉及 BV 数 | 13 支 |
| 6 支 100% junk 视频是否参与提取 | **全部未参与** ✅ |

**结论：考点库没有被污染。** 提取流程正确地只用了 `trusted` 分P。

> 副作用（好事）：这也证明 `_verify2.jsonl` 的 `verdict` 字段**确实被下游用上了**，不是摆设 ——
> 校验机制从"能检测"走到了"被消费"。

### 4.3 建议（按优先级）

1. **先核对污染**：确认 6 支 100% junk 视频有没有参与 `_extract`。有则立即重跑。
2. **按考纲模块归位**：用已有的 `scripts/考点主清单-计算机.json` 做映射。
3. **跨视频合并 + 频次统计**：一个考点被 5 支视频讲过 = 强信号；只被 1 支讲过 = 弱信号。
4. **抽取真题**：正则抓"这是 XX 年的题" → 与 `历年真题/` 交叉验证。
5. **加 L4/L5 校验**。

> ⚠️ **以上 5 条全是工具工作。** 按上一轮诊断的破刀规则：
> **做这些之前，当天必须先有学习落账。** 否则这是第 5 次「完善工具式伪勤奋」。
